# 复盘一次过度设计：删掉 45 万行多面体编译器，换成 40 行最长路

> **TL;DR**：做底层系统容易犯一种职业病，习惯拿依赖库的体量替方案的技术深度背书。为了自动编排推理单步内的预取、引导与旁路训练任务，我们曾往仓库里搬进 45.7 万行 C 代码的多面体编译库（ISL），盘点时才发现它在线上最常干的活是检验整数 `lag >= 1`。本文复盘如何从调度问题的真实几何维度出发，用 40 行一致依赖最长路替换整套重型中端，并分享清掉黑盒之后在剖析器里抓到的多流并发物理真凶。

写底层基础软件的人，心里多少都有点“编译器情结”。只要手头的活涉及循环迭代、跨步数据依赖外加两条 CUDA Stream 的并行编排，脑子里就容易浮现出多面体模型（Polyhedral Model）和整数线性规划——仿佛不先立一套工整的中间表示（IR），直接写几十行图算法就显得不够庄重。

这事不用拿别人举例，我们自己在开发推理引擎扩展层时就结结实实走过一回弯路。

当时的工程需求摆在桌面上挺清楚：往连续批处理引擎里挂载有状态算法时——比如步首跨 PCIe 预取主机内存里的查找表，前向跑完用小网络修正词表分布，采样落定后再在旁路流上跑反向传播与 `AdamW` 更新快权重——运行时必须自动回答三个调度问题：**每个任务在单步内部的哪个时机启动？走主计算流还是旁路流？写出的新状态隔几步对读者可见？**

一看见“循环步”加“跨步依赖”，我们顺理成章搬出了多面体编译领域的基石库 **ISL（Integer Set Library，也是 LLVM Polly 等编译器的核心求解器）**：1,530 个文件、457,770 行 C 代码连同高精度整数库一起进了仓库，外面还用 Rust 搭了一整套自定义的区域中间表示（Region IR），配齐了仿射依赖分析与分块搜索。

现在回头看，当时的心态跟有些县城机修厂贷款买一台航空级五轴联动加工中心差不多：厂里每天接的都是切角铁、车平法兰的寻常活计，压根碰不上五轴联动，但大机器往车间正中间一摆，自己看着踏实，同行来串门时也显得技术底蕴深厚。

---

直到后来我们对生产路径上的每一处真实提速做了一次逐模块盘点，想核对这四十五万行 C 代码到底赚回了多少吞吐，拉出来的清单多少带点黑色幽默。

第一处真正跑出三到六倍提速的地方，是分块状态递推（如 In-Place TTT 与线性注意力变体 GatedDelta）：把形如 $S_t = \mathcal{L}_t(S_{t-1}) + B_t$ 的逐词串行递推改写成 $\mathcal{O}(\log L)$ 的树状并行前缀扫描（Hillis-Steele Prefix Scan）之后，单头 $64 \times 64$ 状态转移耗时从 `1.44 ms` 降到了 `0.22 ms`。可掀开负责识别这项优化的源码一看，干活的其实是一个基于 PyTorch `make_fx` 的轻量代数模式匹配器——它只剥离与状态无关的系数子图，检查状态递推是否落在**标量乘法、对角掩码、左乘矩阵、右乘矩阵**这四种天然满足结合律的线性作用内，**调用 ISL 的代码是零行**，只是最外层套了件自定义 IR 的外套。

第二处真调了 ISL 的地方，是检查旁路流上的在线训练能不能跟下一步的模型前向重叠运行。打开调用现场一看，代码把跨步滞后整数 `lag` 拼成一段多面体集合字符串传进 C 求解器，去验证不等式 `0 <= b < t` 是否成立。说白了，我们唤醒四十五万行的整数线性规划引擎，算了一道口算题：**整数 `lag` 是不是大于等于 1。**

至于那些真把多面体网格展开用满的模块，一遇上多序列并发就撞上了高维格点的组合爆炸：1 条序列求解花 `146 ms`，2 条涨到 `293 ms`，到 4 条序列直接报超出求解配额（`ISL quota exceeded`）；作为对照，不搞多面体展开、直接在模型前向里做矩阵更新一共只要 **`19.6 ms`**。

---

为什么在传统循环编译器里屡试不爽的多面体模型，搬进大模型推理引擎会水土不服？画一张几何结构对比图就明白了。

多面体工具擅长对付的是图像卷积或分块矩阵乘那种三四层嵌套的高维整数格点；可在现代 PyTorch 推理栈里，单个任务内部的算子融合，自带的 `torch.compile`（Inductor）早就比手写中端做得周全了。留给外层运行时去编排的，根本不是高维网格，而是**一条一维时间轴上的 $M = 8$ 个有序阶段锚点**：

```text
单步一维时间轴 (M = 8 个固定锚点):
  0:request.prepare ─► 1:model.execute ─► 2:state.publish ─► 3:sampler.pre_draw
    ─► 4:sampler.complete ─► 5:token.commit ─► 6:request.finish ─► 7:next.prepare

无限展开的跨步循环 (Step t-k -> Step t)          折叠后的有限一致依赖图 (边权 = d - 8k)
  Step t-k:  [ 写任务 u @ a_u ]                        ┌──────────────────────┐
                     │                                 │     边权: d - 0*8    ▼
                     │ (跨 k 步发布, 最小间隔 d)     ┌──────┐              ┌──────┐
                     ▼                              │ 任务u │              │ 任务v │
  Step t:    [ 读任务 v @ a_v ] ──(本步 k=0, d)───► └──────┘              └──────┘
                                                       ▲                      │
                                                       └──────────────────────┘
                                                            边权: d - 8k
```

看上面的折叠过程：每个任务按它读取的输入出生时刻与效果截止时刻，自带初始合法区间 $[a_u^{\min}, a_u^{\max})$。而任意两个任务之间的依赖——不管是同一步内先后读写（$k = 0$），还是第 $t$ 步读取第 $t - k$ 步写出的状态版本（$k \ge 1$，最小间隔 $d$）——只要把第 $t$ 步锚点 $a$ 映射到全局刻度 $T = 8t + a$，不等式两边的步数变量 $t$ 就直接消掉了：

$$(8t + a_v) - (8(t - k) + a_u) \ge d \quad \Longleftrightarrow \quad a_v - a_u \ge d - 8k$$

这就是 1967 年 Karp、Miller 和 Winograd 分析透彻的**一致依赖（Uniform Dependence）**：当跨步距离全是常数时，无穷步的循环直接坍缩成一张只有十来个节点的有限有向图。在上面求每个任务的最早与最晚合法锚点，就是图论里最基础的**差分约束 / 最长路松弛**，用 40 行 Rust 代码就能写完：

```rust
fn propagate(bounds: &[(u32, u32)], edges: &[(usize, usize, i64)]) -> Result<Vec<(u32, u32)>, String> {
    let mut lo: Vec<_> = bounds.iter().map(|b| i64::from(b.0)).collect();
    let mut hi: Vec<_> = bounds.iter().map(|b| i64::from(b.1) - 1).collect();
    for pass in 0..=bounds.len() {
        let mut changed = false;
        for &(u, v, weight) in edges {
            if lo[u] + weight > lo[v] { lo[v] = lo[u] + weight; changed = true; }
            if hi[v] - weight < hi[u] { hi[u] = hi[v] - weight; changed = true; }
        }
        if lo.iter().zip(&hi).any(|(a, b)| a > b) {
            return Err("a task reads a value that exists only after its phase ends".into());
        }
        if !changed {
            return Ok(lo.iter().zip(&hi).map(|(&a, &b)| (a as u32, b as u32 + 1)).collect());
        }
        if pass == bounds.len() {
            return Err("placement constraints contain a contradictory cycle".into());
        }
    }
    unreachable!()
}
```

比起动辄报一句晦涩 `empty set` 的通用整数规划求解器，这 40 行代码的两个报错出口直接对应着人话诊断：`lo > hi` 说明在太早的阶段去读尚未诞生的值（比如采样前去读采样结果）；松弛满轮仍未收敛则说明存在正权环（跨步状态依赖死锁，需调大 `publish_lag`）。删掉那 45.7 万行 C 代码后，规划耗时落回了微秒级。

把重型编译器包袱清出场外、转头打开 Nsight Systems 盯微秒级硬件轨迹时，我们学到了更实在的一课：**白板上画两条并行的 CUDA Stream 箭头不花钱，但在物理硬件上，多流并发只有在两边索取不同资源时才省时间；抢同一块资源时往往是负和博弈。**

下面这三起从剖析时间线上抓出来的减速事故，展示了一套通用的多流排障思路：每当双流重叠没跑出预期加速，先去查**显存总线、跨卡同步障、以及主机内存页属性**这三处争抢点。

```text
事故 A (单卡提早发旁路训练 —— 显存总线踩踏):
  主流:   [ 模型前向 ] ──► [ 采样器全速扫描 80 MB 词表张量 ]
  旁路流:              ──► [ 撤掉栅栏提前启动训练拷贝 + AdamW ]  ◄── 同抢 GDDR/HBM 带宽，总耗时反升!

事故 B (多卡 TP > 1 默认同优先级 —— 跨卡同步障放大抖动):
  主流 (高优 -1): [ 层计算 ] ──► [ Custom All-Reduce 跨卡通信 ] ──► [ 下一层 ]
  旁路流 (普通 0):               [ 本卡等待跨卡链路时，插空跑本地副本训练 ] ◄── 互不抢带宽，冲突归零!
```

1. **盯显存总线饱和度：提早启动旁路流反而更慢。**  
   在 0.5B 模型上跑在线训练时，剖析器显示步末有约 70 微秒的旁路训练露在主流外头。我们曾试着撤掉采样前的等待栅栏，让旁路训练提前跑起来——时间线上露在外面的尾巴确实缩到了 8 微秒，但端到端吞吐反而掉了近两个百分点！看上图事故 A 就清楚了：那个时刻主流采样器正在全力横扫近 80 MB 的词表大表，显存总线早已吃满；提前放出来的训练内核一头撞进采样器怀里抢带宽，两边一起变慢。
2. **盯多卡同步障（Barrier）：用流优先级错开集合通信。**  
   单卡上跑得顺畅的旁路训练，一上多卡张量并行（每张卡各自持有轻量请求状态副本独立更新以省掉通信），吞吐却掉到了原生的 **87%**。拉大时间线一看：多卡每算完一层都要跑紧绷的 Custom All-Reduce，只要某一张卡上的旁路反向内核抢了流处理器、把这张卡进集合通信的脚步拖慢几十微秒，其余所有卡都得在同步障前干等它一个。在 Worker 初始化时用 `torch.cuda.Stream(priority=-1)` 把主干 TP 流设为高优、旁路训练流留在默认优先级 `0` 并错开发布窗口，集合通信重叠冲突直接归零，多卡吞吐回升到了 **97.6%**。
3. **盯主机页属性：警惕 `non_blocking=True` 的假异步。**  
   在健康的异步解码里，CPU 领先 GPU 半步准备路由表（约 700 微秒的 CPU 准备工作藏在几毫秒的 GPU 前向背后）。只要热路径混进**哪怕一次**阻塞同步，CPU 就得等 GPU 排空队列才开始干活，早期版本拔掉最后一次残留同步时吞吐直接从一万一跳到了一万九。而最隐蔽的同步往往没有写 `.item()`——如果你对普通 CPU 张量调 `.to("cuda", non_blocking=True)`，由于普通主机内存是可分页的（Pageable），操作系统随时可能换页，CUDA 驱动不敢让硬件 DMA 后台直读，会在底层悄悄退回同步阻塞拷贝！必须预先分配 `pin_memory()` 锁页环形缓冲，配合 `cuda.Event` 与非阻塞的 `event.query()` 轮转复用，才能拿到实测 6 微秒的真异步上传。

---

这套“40 行一致依赖最长路 + `make_fx` 四类结合律扫描识别 + 多卡流优先级与锁页环形缓冲”的组合，如今就是开源扩展层 **[pLLM](https://github.com/LinesHogan/pLLM)**（`pllm`）的全部调度底盘。

把四十五万行代码删成四十行实在没什么可吹嘘的——毕竟那台用不上的“五轴机床”当初就是我们自己费劲搬进车间的。工程圈子里常有一种隐形激励，觉得搭宏大的编译中端比调一行流优先级更有技术面子，但硬件只按最终落到总线上的指令时序结账。先把边界切干净：单算子融合交给 `torch.compile`，一维阶段编排交给 40 行差分约束，省下的心力留给硬件剖析器。真要是哪天业务里冒出了跨层非一致依赖的高维网格递推，这 40 行小算法肯定兜不住；到那天再去把重武器请回来也不迟。
