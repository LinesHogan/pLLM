# 《苦涩的教训》还有后半句：当商业推理退回“脏先验”，真正卡脖子的是引擎试错税

> **TL;DR**：理查德·萨顿《苦涩的教训》成立的物理前提是单位算力成本持续指数下降；但单晶体管造价企稳与超过 800:1 的算存比，正把大模型训练与推理拉向相反的经济轨道，促使商业推理重新采用多元语法查表、跨层索引复用与测试时快权重这类依赖领域先验的做法。耐人寻味的是萨顿原文的后半句——他反对先验，是因为人类专家的精力无法随算力规模化。今天编码智能体正在把“设计局部先验”变成自动化搜索，反倒是假定“模型只读无状态”的生产推理引擎对每次实验征收三周拉分支重改底层的重税，卡住了搜索闭环。

过去十年，理查德·萨顿（Richard Sutton）的《苦涩的教训》在深度学习圈子里近乎公理：凡是往模型里塞人类先验和精巧局部结构的做法，长远看都会输给“干净统一的架构加海量算力”。

在模型规模一路陡峭爬坡的几年里，现实配合得不错。除了头尾那个带点历史包袱的分词器（Tokenizer），中间几十层 Transformer 规整得像教科书；九十年代自然语言处理学者攒词表、调二元语法（bigram）特征的老手艺，常被拿来当成反面教材调侃。

可最近一两年，翻看前沿团队的推理架构论文与开源代码，风向明显变了。报告里还在赞美简洁架构，生产模型却开始往残差流里挂几百兆的二元、三元语法静态哈希表，把上一层算出的稀疏注意力索引抄给下一层复用，或者在解码时给每个请求挂一块秩为 4 的快权重矩阵边读边做梯度更新——当年被请出正门的统计特征老师傅，换了件印着“稀疏记忆层”的工作服又从后门回来了。

但只要把这些新论文的代码拉下来想测一测并发吞吐，入口处迎面往往是一行断言：

```python
assert len(input_ids) == 1, "only support bs=1 for inference"
```

要是作者团队工程火力足一点，仓库里倒不写 `bs=1`，而是塞进一个几千行改动的 `third_party/vllm-custom` 目录——基线停在半年前的某个提交上，核心调度器与模型执行器被改得面目全非，连作者自己都不敢再往上游同步。算法演进的真实方向，已经和现有推理基建的默认假设顶牛了。

---

为什么大家嘴上推崇简洁，手底下却退回了“脏先验”？把这两年的芯片经济账画出来就清楚了。

萨顿在原文里并没有藏着掖着，他把《苦涩的教训》成立的物理前提写在了明面上：通用简洁的方法之所以总能赢，靠的是摩尔定律——或者更广义地说，**单位计算的硬件成本持续按指数往下掉**。只要多等十八个月算力就能便宜一大截，花人力抠局部结构自然跑不赢直接堆算力。

偏偏这个前提在眼下失灵了。晶圆厂宣传册上的制程名字虽然一路喊到了两纳米、一纳米，但早已脱离物理栅极尺寸；随着光刻层数与建厂资本开支膨胀，单颗晶体管的平均成本出现了持平乃至倒挂。靠缩窄数值位宽挖潜的空间也所剩无几，总归压不穿单比特的物理底线。更紧巴的是存储：DRAM 原始密度多年增长缓慢，主要靠先进封装抬升带宽，把芯片峰值算力与显存带宽的比值拉大到了 **800 比 1** 开外——每从显存搬进芯片一个字节，算术单元得在上面做够八百次运算才不算闲置。

这笔硅片账，头一回把**训练侧**与**推理侧**拽向了两条相反的经济轨道：

```text
训练侧经济账： 用户调用量扩张 ──► 头部厂商聚拢资本堆大集群 ──► 预训练结构洁癖让位于上限，仍可统一扩张
推理侧经济账： 每百万 token 定价决定毛利 ──► 市场倒逼单价年年下探 ──► 硬件不给免费带宽，只能拿结构复杂度换少搬字节
```

顺着推理侧这条线看，最近冒出来的代表性工作全在做同一笔置换——**用离散先验或局部状态，换取更少的显存字节搬运**：
- **用语言离散先验省掉稠密路由**：稀疏加速的本质是把连续潜空间映射回离散分类空间，但常规路由器的矩阵乘本身就要耗算力。DeepSeek 的 Engram 干脆连用两层人类先验——一是人类语言在演化中已经把现实世界切成了离散符号，天然是好索引；二是自然语言的二元、三元词组搭配高度集中，直接拿最近两三个词拼成哈希键去静态大表里取两行向量，连路由矩阵乘都省了（代价也实在：记忆强而计算弱，多轮训练中容易遇到训练损失下降、验证损失反升的过拟合困扰）。
- **用跨层相似先验摊薄索引开销**：长上下文稀疏注意力的打分索引器本身占了大头成本，智谱的 IndexCache 与 DeepSeek 的 CSA2 直接利用“相邻层关注的重点词大同小异”这一经验规律，把一层挑出的索引跨层复用给后续层。
- **用测试期局部更新弥补冻结权重**：面对长尾上下文，与其把整座底座模型翻倍，不如在解码期给每个请求挂一份轻量快权重或预测头（如 In-Place TTT、在线自蒸馏 ESamp、超网络按提示词生成专属 LoRA），边读边改。

既然干的是离散查表与在线修补的活，本质上接近离散组合优化，指望它们保持教科书式的匀质简洁本就不现实。

---

真正值得琢磨的转折，在萨顿《苦涩的教训》的后半段里。

萨顿当年为什么反对往算法里塞人类知识？他在原文里写了三层意思：花在一条路线上的时间就是没花在另一条上的时间；人在心理上会迷恋自己的投入；而且人工知识会把方法搞得盘根错节，难以利用通用算力。翻译成经济学语言，萨顿指出的第二个瓶颈是：**人类专家的注意力没法像算力那样规模化复制。**

放在五年前，这确实是先验路线的死穴——攒一个局部技巧要几个博士生熬大半年。可在今天，编码智能体（Coding Agent）和自动化搜索脚本正在改写等式的这一端：把一篇预印本喂给智能体，一下午就能派生出几十种跨层连接、门控查表或在线损失变体。“设计局部先验”这件事本身，正在变成萨顿自己最推崇的**规模化搜索（Search）**。

按理说，推理期算法的筛选速度应该大幅加快才对。为什么社区里看到的却是一地跑不动并发的 `bs=1` 脚本，和一堆没人维护的 `vllm-custom` 孤儿分支？

因为瓶颈从“想出算法数学”转移到了“穿过服务引擎”。以 vLLM 为代表的现代推理引擎，之所以能把单卡吞吐推高一个数量级，靠的是一条严格的静态假设：**除了一本只往后追加的分页 KV 账本之外，整座模型对并发请求是只读且无状态的。**

```text
研究脚本假设 (bs = 1, 动态可变):
  单条序列独占模型 ──► Python 逐层可插回调 ──► 权重随时 param.add_() 原地覆盖

生产引擎假设 (百路并发, 静态只读):
  多租户词元拍扁成二维表 [tokens, H] ──► 算子融合并录死进静态 CUDA Graph ──► 主旁流无锁异步推进
```

一旦新算法带上了每请求可变状态或跨层读写，两条常规路径就都走不通了：留在单流 Hugging Face 循环里，吃不到连续批处理与静态图，来四个并发请求就得排队串行；要是拉一个 vLLM 私有分支进去硬改，为了跑对二十行算法数学，就得手工从扁平表里还原行归属、给静态图预留固定基地址池、防备主旁双流读写撕裂、处理 KV 抢占重算时的状态回滚，还得对齐多卡张量并行分片。花三周排完雷，上游升两个版本改一轮内部签名，分支就成了负资产。每验证一个点子先交三周“引擎改造税”，再快的自动化搜索也转不起来。

---

怎么把这笔试错税从三周压回半小时，同时又不退化成按论文名字堆砌的专属补丁？

可以借鉴当年 Linux 内核引入 eBPF 替代私有内核模块的分层思路：不改上游引擎源码，沿着硬件资源的真实边界，把有状态推理期计算拆成四个正交声明——**状态归谁**（单请求私有还是实例共享）、**如何演化**（步后优化器求导、前向内分块递推、超网络生成还是在线热导入）、**作用在哪**（残差交界、分页/潜空间注意力、线性投影叠加还是采样尾声），以及**隔几步可见**。

我们做开源项目 **[pLLM](https://github.com/LinesHogan/pLLM)**（`pllm`，直接架在原版 vLLM 之上运行的可编程层），就是为了验证这套拆法能不能立住。以在线自蒸馏引导（ESamp）为例——每个并发请求各自维护一个秩为 4 的双层小网络，每步拿第 0 层隐藏状态拟合末层隐藏状态做 `AdamW` 在线训练，同时在采样前压低浅层就能猜中的候选词——声明出来只是十几行标准 PyTorch：

```python
from dataclasses import dataclass
import torch
from torch import nn
import pllm


@dataclass(frozen=True)
class ESampLite(pllm.Workload):
    beta: float = 0.5
    distiller = pllm.RequestState(
        init=pllm.FromModule(
            lambda m: nn.Sequential(nn.Linear(m.hidden_size, 4), nn.Linear(4, m.hidden_size))
        ),
        optimizer=pllm.AdamW(1e-3),
    )

    @pllm.train(state="distiller")
    def loss(
        self,
        shallow: torch.Tensor = pllm.hidden(0),
        deep: torch.Tensor = pllm.hidden(-1),
        f: nn.Module = pllm.module("distiller"),
    ) -> torch.Tensor:
        return (f(shallow.float()) - deep.float()).square().mean(-1)

    @pllm.guide_sampling(beta=pllm.cfg("beta"))
    def predict(
        self,
        shallow: torch.Tensor = pllm.hidden(0),
        f: nn.Module = pllm.module("distiller"),
    ) -> torch.Tensor:
        return f(shallow.float())
```

块表寻址、多版本槽池、把反向传播录进旁路流静态图与下一步前向重叠、乃至采样尾声只挑幸存词做点积，全部下沉到了运行时内部。在 7B 模型、128 并发序列下，这套边训边引的完整流水线能维持原生引擎 **96% 以上**的吞吐；把社区 4B 规模的 In-Place TTT 检查点按同一套声明接进来，不仅单请求比官方单流脚本更快，4 并发吞吐还能翻倍，且无需改动代码即可挂到兼容 OpenAI 协议的流式服务后面运行。

当然，不拆宿主引擎的前提是守宿主的物理规矩，这层抽象也有它明确的红线。为了进静态图并守住多租户隔离，方法体里不能写依赖张量数值的 Python 分支或跨行归约；像 H2O、SnapKV 那类要求按运行时注意力分数在序列中间动态释放物理 KV 块的算法，因为直接冲突于 vLLM 单标量进度与只追加块表的底层记账模型，框架照样无法支持，只能在启动检查时直接报错说清原委。况且芯片封装本身也在演进，倘若过几年 3D 堆叠存储把算存比往回扳一个量级，今天流行的不少离散先验或许又会退潮。基础设施不必替未来押注赢家，能帮眼下探路的人省掉那三周脏活、让新想法凭真实并发评测而不是凭改引擎的体力定生死，就够本了。
