# 数学公式一字不差，Triton 内核却算出 `1` 而 PyTorch 算出 `0`：混合精度融合算子里的两次舍入排障

> **TL;DR**：把手写 Triton 融合内核投入半精度推理之前，最容易踩中的坑不是写错公式，而是“在 `float32` 累加器里多留了一步没舍入，或者少做了一次标量类型截断”。本文复盘动态切层开发中抓到的两处真实精度分叉：一处是 `FP16` 下输入 `[2048, 0]` 触发大数吃小数（吸收效应），导致融合仿射内核算出 `1` 而原生 PyTorch 算出 `0`；另一处是在多卡张量并行 `down_proj` 输出 `FP32` 部分和时，因忽略了 Python `float` 标量的弱类型规则导致缩放因子 `0.123` 出现尾数偏差。文末总结如何用单位末位（ULP）边界探针与跨步长哨兵列替代笼统的 `randn` 容差测试。

写 GPU 算子的人大都有过这种错觉：只要把 PyTorch 参考函数里的线性代数公式一字不差翻译成 Triton，并且为了“数值更准”全程用 `tl.float32` 做乘加累加、只在写回显存那一刻转回 `float16` 或 `bfloat16`，算出来的结果就算跟 PyTorch 原生算子有一丁点尾数出入，也肯定是我们的 `float32` 融合版更精确，拿 `torch.testing.assert_close(..., rtol=1e-2, atol=1e-2)` 测测标准正态随机数过关就行了。

直到在审查低秩仿射激活干预（LoReFT，公式为 $\Delta h = R(Wh + b - R^\top h)$）与张量并行 LoRA 内核时，两组只有两维的极简输入直接把这种侥幸心理打醒了。

第一组输入跑在 `float16` 下：隐藏状态 $h = [2048, 0]$，投影行向量 $W = [1, 1]$，正交基列向量 $R^\top = [1, 1]$，偏置标量 $b = 1$。  
代进纸面数学公式口算：$Wh = 2048$，$R^\top h = 2048$，括号里 $2048 + 1 - 2048 = 1$，乘上 $R$ 得到增量 $[1, 1]$，加回 $h$ 后第 1 维结果显然该是 `1`。我们的 Triton 内核确实算出了 `[2049, 1]`；可转头跑一遍线上已有的 PyTorch 原生实现 `(h @ W.T + b - h @ R) @ R.T`，它算出来的第 1 维却是干脆利落的 **`0`**。

如果说第一组是“数学上该得 1，PyTorch 却得 0”，紧接着在多卡张量并行（`TP > 1`）的 `down_proj` 路径上测到的第二组数就更挠头了：`bfloat16` 输入产生 `27.0` 的投影修正值，乘上缩放系数 `scale = 0.123`，累加进 `float32` 类型的跨卡待规约输出缓冲 `output` 里——PyTorch 原生路径加进去的是 **`3.328125`**，而我们的 Triton 内核加进去的是 **`3.3210001`**。

两边写的都是最基础的乘加，既没超越函数也没随机丢弃，这两处偏差到底是从哪条指令缝里钻出来的？

---

先拆第一桩悬案：为什么 `2048 + 1 - 2048` 在 `float16` 的原生 PyTorch 里等于 `0`，进了融合 Triton 内核却等于 `1`？

这得把 `2048` 放到 IEEE 754 半精度浮点数（`float16`：1 位符号、5 位指数、10 位显式尾数，外加 1 位隐含前导 `1`）的数轴刻度尺上看。

在 `[2048, 4096)`（即 $[2^{11}, 2^{12})$）这个区间里，指数固定为 $2^{11}$。10 位尾数一共只能切分出 $2^{10} = 1024$ 个等距格子。用区间长度 $2048$ 除以 $1024$ 个格子，相邻两个可表示浮点数之间的最小间距——也就是**单位末位（ULP，Unit in the Last Place）**——刚好等于 **`2.0`**：

```text
IEEE 754 float16 在 [2048, 4096) 区间的真实可表示刻度（尾数 10 bit，ULP = 2.0）：

  ... ───┼──────┴──────┼──────┴──────┼──────┴──────┼─── ...
       2048.0   ▲    2050.0        2052.0        2054.0
                │
            2049.0 恰好落在两个刻度的正中间！
            按 IEEE 754 默认“向最近偶数舍入（Round to Nearest, Ties to Even）”：
            2048 的末位尾数是 0（偶），2050 的末位尾数是 1（奇）──▶ 2049.0 被直接吸回 2048.0！
```

看清了这把刻度尺，再对比原生 PyTorch 与第一版 Triton 内核求值顺序的差异，真相就全清楚了。

在原生 PyTorch 里，表达式 `h @ W.T + b - h @ R` 并不是一口气算完的，而是拆成四条独立的 ATen 算子依次落盘，每条算子算完都要把结果舍入回输入张量的 `float16` 类型：
1. 算 `wh = h @ W.T`，得到 `float16(2048.0)`；
2. 算 `wh_b = wh + b`，也就是 `float16(2048.0 + 1.0)`——撞上刚才的偶舍入规则，`1.0` 被大数 `2048.0` 吸收，结果依然是 `float16(2048.0)`；
3. 算 `hr = h @ R`，得到 `float16(2048.0)`；
4. 算 `wh_b - hr`，即 `2048.0 - 2048.0 = 0.0`！

而在第一版 Triton 融合内核里，我们把两次内积的累加器 `acc_w`、`acc_r` 和偏置 `b` 全留在了尾数高达 23 位的 `tl.float32` 寄存器里（在 `2048` 附近，`float32` 的 ULP 只有 $2^{-12} \approx 0.000244$），直接写了 `(acc_w + b - acc_r).to(fp16)`。在 `float32` 寄存器里，`2048.0 + 1.0` 精确等于 `2049.0`，随后减去 `2048.0` 发生相消，把原本在半精度下已经被吃掉的 `1.0` 原样留了下来！

也许有人会问：“留着 `1.0` 难道不是更贴近实数数学吗？为什么要改回去？”

这就是单写科研脚本与做推理引擎底座的分水岭：在引擎里，用户今天可能先用静态单层 `ActivationPatch(layers=(10,))` 标定好一组干预参数和评测基准（跑的是既有参考算子），明天为了在线切层换上 `LayerRoute.patch(over=(2, 10, 18))`。如果两个入口对同一组权重、同一个第 10 层给出不同的舍入点，在 `temperature=0` 的贪婪解码或 `top-p` 截断边界上，一步 `1` 个 ULP 的分歧在自回归滚雪球三五步之后就会演变成整句输出分道扬镳，用户根本分不清是切层逻辑有错还是算子偷换了精度。

要在早退融合内核里严守与静态参考算子的数值契约，其实不需要退回慢速的多算子写显存——只需在 Triton 寄存器里显式复刻那三次类型截断即可：

```python
# 在寄存器内复刻 ATen 逐步落盘的模型精度舍入点，零额外 HBM 流量：
wh = acc_w.to(elem_ty).to(tl.float32)
wh_b = (wh + b).to(elem_ty).to(tl.float32)
hr = acc_r.to(elem_ty).to(tl.float32)
coeff = (wh_b - hr).to(elem_ty).to(tl.float32)
```

四行寄存器内的 `.to(elem_ty)`，既保住了单内核融合与未命中早退的带宽优势，又让 `float16` / `bfloat16` 的每一步舍入行为与原生算子逐位对齐。

---

再拆第二桩悬案：为什么 `27.0 * 0.123` 在张量并行的 `down_proj` 上会出现 `3.328125` 与 `3.3210001` 的分歧？

先把现场的张量类型对齐。在单卡（`TP = 1`）下，模型隐藏态 `hidden` 是 `bfloat16`，线性层输出 `output` 也是 `bfloat16`。但在多卡张量并行（`TP > 1`）下，`down_proj` 是一个按输入特征维切分的**行并行线性层（`RowParallelLinear`）**——每张卡各自算出一个局部部分和，最后经过一次跨卡 `All-Reduce` 相加得到完整输出。为了避免每张卡在 `All-Reduce` 之前各自做一次 `bfloat16` 舍入叠加误差，我们在钩子里特意让多卡 `down_proj` 的基础部分和保持在 **`float32`**，等本卡的 LoRA 修正量也加进去、做完跨卡 `All-Reduce` 后，再统一转回 `bfloat16`。

也就是说，在进入 LoRA 累加的那一刻：`hidden` 和算出来的未缩放 LoRA 矩阵乘结果 `result`（值为 `27.0`）是 **`bfloat16`**，Python 缩放系数 `self.scale`（值为 `0.123`）是 Python 原生 **`float`**（底层是 64 位双精度），而目标缓冲区 `output` 是 **`float32`**。

现在看静态参考路径里的这行普通得不能再普通的 Python 表达式：

```python
output[:, offset : offset + width].add_((result * self.scale).to(output.dtype))
```

问题就出在 `result * self.scale` 的结果到底是什么类型！

凭直觉猜，不少人会以为“`bfloat16` 乘 64 位 `float`，精度肯定往高处走，变成 `float32`”。但 **PyTorch 的类型提升格（Type Promotion Lattice）对“张量 × Python 标量”有一条专门的弱类型降级规则**：Python 的 `float` / `int` 标量属于第 0 级弱类型，当它与任意浮点类型的 `Tensor`（哪怕是低精度的 `float16` 或 `bfloat16`）做算术运算时，**除非发生溢出，否则运算结果严格保持该 `Tensor` 的原有低精度类型，绝不会把张量提升成 `float32`！**

把两边的类型流转画出来，那 `0.007` 的差距是怎么来的就一清二楚了：

```text
【静态参考路径：(result_bf16 * 0.123).to(fp32)】
  result (bf16: 27.0) × scale (Python float: 0.123)
   ──▶ 触发弱类型标量规则，乘法输出仍被截断为 bfloat16！
   ──▶ 实数积 3.321 在 [2.0, 4.0) 区间（bf16 尾数 7 bit，ULP = 2 / 128 = 0.015625）：
       212 × 0.015625 = 3.3125，213 × 0.015625 = 3.328125 ──▶ 舍入为 bf16(3.328125)
   ──▶ .to(output.dtype) 拓宽为 fp32 ──▶ 最终加进部分和的是 3.328125！

【第一版 Triton 内核：(corr_bf16.to(fp32) * scale).to(out_dtype)】
  corr (bf16: 27.0) ──▶ .to(fp32) × 0.123 = fp32(3.3210001)
   ──▶ 单卡时 out_dtype 是 bf16，恰好也会被截成 3.328125（所以单卡测试全绿！）
   ──▶ 多卡 TP>1 down_proj 时 out_dtype 变成了 fp32，3.3210001 没经过 bf16 量化就直通写进了 output！
```

多妙的一个隐蔽耦合：在单卡测试里，因为 `output` 本身就是 `bfloat16`，最后一步 `.to(out_ptr.dtype.element_ty)` 歪打正着替我们补上了那次 `bfloat16` 截断，掩盖了中间少做的一次舍入；一到多卡 `down_proj` 把 `output` 换成 `float32` 部分和，遮羞布一揭开，动静两条路径立刻失配。

在内核里把那次隐藏的 `hidden.dtype` 标量乘法截断补齐，两套路径在单卡与多卡下就逐位一致了：

```python
corr = acc.to(hidden_ptr.dtype.element_ty)
# 复刻 PyTorch (bf16_tensor * python_float) 的原类型截断，再拓宽至输出缓冲区类型：
scaled = (corr.to(tl.float32) * scale).to(hidden_ptr.dtype.element_ty)
delta = scaled.to(out_ptr.dtype.element_ty)
```

顺着同一轮内核走查，我们还修掉了另一个由“默认连续内存假设”引发的隐患：原先写回切片地址时写了 `row * out_stride0 + out_offset + cols`，默认输出矩阵列步长 `out_stride1 == 1`。这在常规的连续 QKV 拼接切片 `output[:, offset:offset+width]` 上完全成立（因为切片只改偏移不改列步长），但如果调用方传入一个隔列采样的非连续视图 `output[:, ::2]`（此时 `out_stride1 == 2`），内核就会越界写坏奇数位置的邻居列。显式传入 `out_stride1` 并改成 `row * out_stride0 + (out_offset + cols) * out_stride1`，只多一个整数乘法，就能把任意二维视图步长全部兜住。

---

这两次排障放在一起，对平时写高性能内核测试有两个直接启发。

第一，**别拿零均值高斯随机张量（`torch.randn`）加放宽的 `rtol=1e-2` 当护身符，更别让“参考值”和“待测值”走同一段底层辅助函数。** `randn` 生成的数大多集中在 `[-2, 2]` 附近，指数接近一致，几乎不会撞出大数吃小数的吸收边界；而专门构造一组像 `FP16 [2048.0, 0.0] + 1.0` 这样横跨 ULP 吸收阈值的二维极简探针，外加一组非二进分数缩放因子（如 `0.123`）配 `float32` 输出缓冲，不用加载任何模型权重，十行代码就能把舍入契约验个底朝天。

第二，**测切片与视图写回时，养成在目标视图外围填满哨兵值（Canary，比如 `-99.0`）的习惯。** 像 `out = torch.full((1, 4), -99.0); kernel(..., out[:, ::2])` 这样跑完之后，不仅要查偶数列 `out[:, ::2]` 算对了没有，还要查奇数列 `out[:, 1::2]` 是不是还纹丝不动地保持着 `-99.0`——但凡算错一个步长偏移，哨兵列第一时间就会报警。

上述精度对齐后的早退内核目前均已在 **[pLLM](https://github.com/LinesHogan/pLLM)** 中上线并通过实卡逐位校验（`rtol=0, atol=0`）。需要说明的是，在寄存器里显式做半精度中间截断，目标是与未融合的标准算子保持严格的代数与舍入等价；如果业务场景并不存在对应的静态单算子基准、纯粹追求最高数值信噪比，保留全 `float32` 中间累加反而是更自然的选择——关键不在于哪一种“绝对正确”，而在于你写下的每一处类型转换都应当是有意识的决策，而不是被编译器或类型提升规则悄悄替你决定的意外。
