# Configuration Options

This page lists every field of `pllm.ModelConfig`, `pllm.ExecutionOptions`, `pllm.KVOffload`, `pllm.host.HostConfig`, and `pllm.benchmark.BenchmarkOptions`. The "Field" and "Default" columns are generated from code by `tools/check_docs.py --write-generated`, while the remaining columns are hand-authored; byte sizes are in bytes.

```python
import pllm
from pllm.workloads import DummyWorkload

config = pllm.ModelConfig(
    "Qwen/Qwen2.5-0.5B-Instruct",
    max_num_seqs=64,
    max_num_batched_tokens=4096,
    gpu_memory_utilization=0.5,
    execution=pllm.ExecutionOptions(publish_lag=1, state_page_budget_bytes=256 << 20),
)

print(pllm.explain(DummyWorkload(), config).eager_reason == "")
```

## ModelConfig: Model and Engine

Most fields are forwarded to vLLM unchanged and share the same meaning as vLLM's parameters of the same name; fields prefixed with "pLLM:" are interpreted by pLLM.

<!-- ModelConfig fields: generated by tools/check_docs.py --write-generated; do not edit -->
| Field | Default | Meaning | When to Change |
| --- | --- | --- | --- |
| `model` | Required | Hugging Face model name or local path | — |
| `dtype` | `"bfloat16"` | Precision for model weights and activations: `"bfloat16"`, `"float16"`, `"float32"` | Rarely changed; `"auto"` state dtype follows this setting |
| `max_model_len` | `512` | Maximum prompt plus generated tokens per request | Increase for long prompts or long generations; KV memory grows accordingly |
| `max_num_seqs` | `8` | Maximum number of concurrent running requests | Commonly 128 for throughput benchmarks; pLLM scales per-request state reservations with it |
| `max_num_batched_tokens` | `512` | Maximum tokens computed per step (including prompt chunks) | Increase when serving many long prompts; also sets the row cap for `tokens="all"` exports |
| `gpu_memory_utilization` | `0.5` | Fraction of GPU memory available to vLLM (weights, KV cache, and pLLM reservations all fit inside this) | Adjust when short on VRAM or sharing the GPU with another engine |
| `kv_cache_memory_bytes` | `None` | KV cache size in bytes; `None` lets vLLM size it from free VRAM measured at startup | Set when another process allocates/frees VRAM on the same GPU (which can break startup profiling) or to pin a fixed KV size |
| `seed` | `0` | Global vLLM RNG seed and seed for pLLM state initialization (`pllm.Computed`, module init); per-request sampling seeds go in `SamplingParams(seed=...)` | Pin for reproducible experiments |
| `trust_remote_code` | `False` | Allow loading code from the model repository | Only for models requiring remote tokenizer code (e.g., Kimi slices) |
| `enable_prefix_caching` | `False` | vLLM prefix caching | May be enabled for read-only workloads, `Adapter` reading only immutable `InstanceState` (non-`Imported`/`Fed`, no writer methods), stateless `@pllm.custom_residual`, and static `ActivationPatch` with `last_tokens=0`; must be disabled when using `RequestState`, mutable/externally written `InstanceState`, `last_tokens > 0`, `@pllm.train_in_forward`, or `@pllm.custom_attention` |
| `enable_chunked_prefill` | `False` | vLLM chunked prefill | Enable when mixing long prompts with decode; prompt-row training runs per chunk |
| `generated_kv` | `"isolate"` | pLLM: whether KV entries of generated tokens can be reused as prompt prefixes by later requests when prefix caching is enabled. When a workload distinguishes prompt and generated tokens (e.g., an activation patch modifying only generated tokens), the same token yields different KV depending on role; `"isolate"` prevents such reuse | Set to `"reuse"` only if you know generated KV does not depend on whether a token is prompt or generated |
| `revision` | `None` | Model repository revision | Pin a specific checkpoint revision |
| `multiprocessing` | `"auto"` | pLLM: whether to isolate the workload inside vLLM's `EngineCore` subprocess (`"auto"` / `True` / `False`) | Default `"auto"` enables subprocess isolation for `pllm.make_async_llm`, `pllm serve`, and `tensor_parallel_size > 1`, and stays in-process for single-GPU `pllm.make_llm`; see requirements in [Production Deployment](../howto/production.md) |
| `execution` | `ExecutionOptions()` | pLLM execution policy; see next section | — |
| `cuda_graphs` | `"auto"` | pLLM: `"auto"` uses CUDA graphs when possible, otherwise falls back to eager and records the reason in `eager_reason`; `True` requires graph capture and errors if impossible; `False` forces eager | Set `True` during throughput benchmarks to prevent silent fallback to eager |
| `kv_offload` | `None` | Offload full KV pages to CPU memory; see `KVOffload` | When KV VRAM is tight and long context must be retained |
| `tensor_parallel_size` | `1` | Number of tensor-parallel GPUs | Requires vLLM 0.32.0+; see [Support Matrix](support-matrix.md) for supported features |
| `pipeline_parallel_size` | `1` | Pipeline parallelism | Must currently be 1; pLLM supports tensor parallelism only |
| `data_parallel_size` | `1` | Data parallelism | Must currently be 1; pLLM supports tensor parallelism only |
<!-- end of generated ModelConfig fields -->

## ExecutionOptions: pLLM Execution Policy

<!-- ExecutionOptions fields: generated by tools/check_docs.py --write-generated; do not edit -->
| Field | Default | Meaning | When to Change & Cost |
| --- | --- | --- | --- |
| `max_host_training_rows` | `1` | Maximum rows (sequences) per state accepted per step by host-batch training | Increase for larger host batches; pLLM reserves training VRAM based on it. Does not limit decode request rows |
| `cuda_graph_pool_budget_bytes` | `None` | Private CUDA graph memory pool budget per task and for the model (not a combined total); `None` reserves per traced task size and lets vLLM manage the model graph | Increase to the byte count reported in an error when told how many bytes are needed (common with stateful sublayers and `custom_forward`) |
| `state_page_budget_bytes` | `0` | VRAM page budget for state; `0` uses the free capacity observed by the backend | Specify an explicit value to make plans reproducible or cap state footprint |
| `execution_peak_budget_bytes` | `None` | Cap on pLLM peak execution memory: state pages, task workspaces and live results, CUDA graph pools, and anchor reservations (excludes model weights and KV cache); `None` is uncapped | Below the overlap threshold printed by `explain`, side-stream tasks fall back to main-stream inline execution (no overlap); below the failure threshold, planning errors |
| `allow_numerical_transforms` | `True` | Allow pLLM to rewrite numerical paths for speed (fusion, parallel scan); floating-point rounding may change, emitting a one-time warning when used | Set `False` when bit-exact agreement with a reference implementation is required |
| `tuning` | `"heuristic"` | `"heuristic"` selects implementations using deterministic rules; `"measured"` benchmarks at startup and picks the faster implementation | Use `"measured"` when trading startup time for measured kernel selection |
| `publish_lag` | `1` | An update computed at step n by training or writing becomes visible for reading starting at step n + 1 + `publish_lag` | Set `0` for strict ordering (step n updates visible at step n + 1), at the cost of losing overlap between training and the next forward pass; see [Core Concepts](../explain/core-concepts.md) |
| `guidance_capacity` | `4096` | `@pllm.guide_sampling` guides only the top this many logits per row after top-k / top-p filtering, leaving the tail unguided; must be a power of 2 between 32 and 4096, or `None` for exact guidance over the full vocabulary | Increase if the surviving candidate set is often larger; smaller values can be slower because exceeding rows take top-K selection |
<!-- end of generated ExecutionOptions fields -->

## HostConfig: Host-Only Training Workloads

`pllm.host.make_host(HostConfig(...), workload)` compiles the workload using these facts without loading a model (see [Host Loops and Batch Training](../guides/host-loops.md)).

<!-- HostConfig fields: generated by tools/check_docs.py --write-generated; do not edit -->
| Field | Default | Meaning |
| --- | --- | --- |
| `device` | Required | Device where training runs, e.g., `torch.device("cuda")` or `torch.device("cpu")` |
| `hidden_size` | `0` | Width of hidden rows in a batch |
| `target_shape` | `()` | Per-row target shape; `()` means one scalar per row |
| `seed` | `0` | RNG seed for state initialization |
| `state_page_budget_bytes` | `67108864` (64 MiB) | State page budget |
| `max_input_rows` | `None` | Maximum rows per batch; larger batches are rejected before `train` |
| `execution_peak_budget_bytes` | `None` | Per-step execution peak memory cap |

## BenchmarkOptions: Aligned Throughput Comparison

Used by `pllm.benchmark.compare` and `tools/benchmark_*.py` (see [Measuring Throughput Fairly](../howto/measure-throughput.md)).

<!-- BenchmarkOptions fields: generated by tools/check_docs.py --write-generated; do not edit -->
| Field | Default | Meaning |
| --- | --- | --- |
| `model` | `"Qwen/Qwen2.5-0.5B-Instruct"` | Model |
| `batch` | `8` | Number of prompts |
| `tokens` | `256` | Number of generated tokens per sample (ignoring EOS) |
| `rounds` | `3` | Timed rounds (median is reported) |
| `warmup` | `1` | Untimed warmup rounds |
| `gpu_memory_utilization` | `0.25` | GPU memory fraction per engine |
| `profile` | `None` | When set to a directory, runs an additional profiling pass after timing |
| `cuda_graph_pool_budget_bytes` | `None` | CUDA graph capture pool budget; defaults to automatic sizing |
| `state_page_budget_bytes` | `0` | State page budget; defaults to automatic sizing |
| `execution_peak_budget_bytes` | `None` | Execution peak memory cap |
| `sampling_n` | `16` | Number of samples per prompt |
| `cuda_graphs` | `True` | Enable CUDA graphs on both engines |
| `guidance_capacity` | `4096` | Same as `ExecutionOptions.guidance_capacity` |
<!-- end of generated BenchmarkOptions fields -->
