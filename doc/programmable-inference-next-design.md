# 可编程推理：精简完成后的进一步设计方案

日期：2026-09-06。状态：设计建议，尚非已实现能力或实验结论。

本文描述 [架构精简计划](architecture-consolidation-10k-plan.md) 完整实施后的下一阶段。
不替代当前删除、功能补齐和证据验收，也不授权建立第二套 runtime。
PTTS/AER 的具体设计仍以现有研究文档为权威；本文提出面向算法、systems 和工程开发的
共同目标。发生设计冲突时应先明确修订权威契约，不能让两种解释同时进入实现。

## 1. 核心与成功标准

核心主张：**把算法对推理过程的修改，编译成语义正确、资源高效的执行。**

框架允许自定义计算、状态更新与条件重放，并保留足够的语义信息供系统分析和优化。
推理与在线学习协同调度是重要实例，但不能把全部算法限制为参数更新。
layer replay、activation intervention、条件循环也属于目标表达范围。

成功需要同时满足四种体验：

| 使用者 | 应当获得的能力 |
| --- | --- |
| 算法研究者 | 数学、梯度、循环和更新时机直接可见，能够定位数值偏离与状态污染 |
| Systems 研究者 | 决策空间与约束明确，可替换策略并解释性能收益及适用条件 |
| GPU/backend 工程师 | buffer 所有权、stream/event、capture、KV 和版本生命周期能够追踪 |
| 人类及 agent 开发者 | 能找到唯一 owner，以局部修改完成扩展，并执行明确、可复现的验证 |

行数、模块数和技术栈不单独构成质量证明。高质量设计应减少理解一个行为必须跨越的
文件与隐含约定，同时保留真实职责边界；不采用万能文件或机械切分的小模块。

## 2. 两种自由度与可分析性

算法表达自由度决定能描述哪些计算；系统优化自由度决定在固定算法语义下能改变哪些安排。
二者不能混淆。强顺序循环可以很有算法价值，但没有多少并行空间。

- 算法声明数学、因果依赖、状态作用域、梯度边界、执行条件和允许的可见性。
- 系统决定合法的启动时机、并行、批处理、region、placement、传输与存储表示。
- 算法允许有界陈旧或延迟发布时，必须显式给出允许范围。系统不得自行放宽。
- 自定义数学可作为实现单元；其读写状态和影响执行合法性的副作用必须显式。
- 未声明的外部副作用不得被当作纯计算优化；无法描述的操作应在边界拒绝或作为明确的
  不可重排操作处理，具体策略进入能力契约，不能偷偷降级。

静态可分析区域交给现有规划机制；依赖运行结果的控制流在显式边界推进。
多面体与 DP 的适用范围需据依赖结构说明，不强行展开所有循环为完整静态 DAG。
在线选择依然受同一规划 authority 控制；worker 只执行已授权决策，不能另设本地调度策略。

## 3. 表达能力：以组合验证，而不是枚举算法

首轮选三个机制：附加计算、版本状态更新、条件 layer replay。用一个代表性算法组合它们，
再用未参与接口设计的算法变体检验通用性。

| 语义 | 必须表达的事实 |
| --- | --- |
| 自定义数学 | 输入输出、shape/dtype 约束、状态访问、梯度是否保留及截断位置 |
| 状态更新 | request/global 作用域、读版本、写目标、发布可见性和更新频率 |
| 条件控制 | 条件数据依赖、循环携带值、终止条件、迭代上限及请求取消规则 |
| Layer replay | 层范围、token/row 选择、参数版本、KV/RNG effect、输出用途和梯度边界 |

已有能力能够表达的变体，应只修改算法声明与数学实现；真正的新模型机制才扩展 backend。
不以任意 Python hook/callback 提供表面自由度，也不提前设计覆盖所有算法的巨大 DSL。
接口首先应自然表达参考算法，符号与概念尽量对应论文和朴素 PyTorch 实现。

## 4. 副作用、所有权与失败语义

计算完成、结果发布和资源释放是三个独立事件。任何异步操作都应能回答以下问题：

| 边界 | 契约要求 |
| --- | --- |
| Tensor mutation | 区分私有工作区写入和可观察状态变化；说明别名和独占写约束 |
| Version publication | 明确原子范围、可见对象、提交点与 exact pin |
| KV/replay | 声明读取、追加、覆盖、分支或失效；不能假定 replay 没有 cache effect |
| RNG | 明确随机流作用域及推进规则；记录重现需要的身份或状态 |
| Host service | 明确重复调用、幂等性、重试和外部不可逆副作用 |
| CUDA completion | 用 issued receipt/event 证明完成，完成前不得回收或覆盖仍被使用的存储 |

每项资源只有一个生命周期 owner。借用、pin、publish 和 retire 必须有可追踪的关系；
调用方不能靠约定推测另一个模块是否还会使用 tensor。
CPU/CUDA 共享语义状态转换，device-specific 差异放在 provider 的实际操作和完成机制。

失败按提交点定义：提交前可取消或回滚的内容、提交后必须结算的内容、正在运行且只能
等待的 GPU 工作分别处理。不能通过捕获异常后重试整个 step 造成重复更新或重复 host effect。
少量故障注入覆盖部分 admission、publication 前后失败、请求取消、迟到 completion 等边界。

## 5. 数据结构与抽象设计

建议保持下列职责区分；这是概念边界，不要求每行新建一个包或 DTO 家族。

| 数据/组件 | 职责 | 不应承担 |
| --- | --- | --- |
| Authoring descriptor | 数学、数据流、effect、timing/control constraints | lane、stream、设备选择策略 |
| Semantic representation | 稳定语义身份、依赖与控制区域 | Tensor handle、backend 对象 |
| Physical decision | 已确定的实现、资源映射、执行与发布约束 | callback、worker 再选择 |
| Invocation state | 某次请求/迭代的动态值、游标、receipt | 跨运行全局隐式状态 |
| Resource owner | buffer、版本、pin、completion 和回收 | 算法 objective 与调度策略 |
| Backend primitive | 模型/设备的具体操作及 capability facts | workload 特判和隐藏的状态 authority |

- 使用有含义的 ID 和封闭 variant；避免多个 bool 组合出非法状态。
- 区分 request、iteration、logical version、physical allocation、task，不能共用裸整数的含义。
- 编译后描述默认不可变，执行中的可变状态局部化；不靠复制整份 config 表达状态转换。
- 每项事实有唯一来源；派生索引明确由谁生成、何时失效，不维护多份可独立修改的真相。
- 显式传递窄的依赖，避免装有所有服务的 Context/service locator。
- DTO 只承载数据；代码实现通过显式、typed 的绑定关系注册，不能把 Callable 塞入 wire DTO。
- Python/Rust 动态解码留在 codec；backend 外部对象操作集中在 adapter。
  不为内部类型保证重复增加运行时守卫，也不以反射发现替代明确接口。
- 先验证真实的第二个使用场景再提取共享抽象；避免为假想扩展建立 registry/plugin 层。

## 6. 系统分析与算法调试的共同基础

维护可关联的来源链：

```text
算法定义位置 -> 语义 operation/control region -> 编译后的任务
             -> invocation/request/iteration -> 实际执行事件
             -> 读取版本 / 发布版本 / completion / retire
```

融合与重排是多对多映射；不能只记录一个 source line 丢失来源。
语义 identity 与运行期 invocation identity 分开，便于比较不同计划和多次实验。
对外序列化的诊断数据标明 schema；版本演进集中处理，不在每个消费者里添加兼容分支。

同一份执行事实支持不同视图：

| 算法调试 | 系统分析 |
| --- | --- |
| 输出用了哪个版本、哪轮 replay | 等待哪个依赖、publication 或资源 |
| 哪一步首次偏离 reference | capture、计算、通信、同步各花多少成本 |
| 更新是否影响了其他请求 | 版本驻留、峰值内存和 admission 压力 |
| 梯度是否截断、监督是否泄漏未来信息 | 哪些合法优化因约束或 backend 能力不可行 |

默认记录有界、低成本的元数据；详细 trace、tensor/gradient snapshot 按请求、节点或迭代筛选。
明确内存上限、溢出行为和保留策略，不默认保存 prompt、用户数据或所有中间 tensor。
记录调试是否插入同步、影响 capture 或改变时序；不能把调试模式性能当作正常执行性能。
跨设备计时说明时钟与关联方法，host launch 时间不冒充 GPU execution 时间。

优先提供可读取的计划、结构化 trace 和定位工具，再考虑 dashboard。
支持选定操作的输入捕获与 reference 对照；独立 replay 需要闭合的输入、版本、KV/RNG 等
依赖。缺失依赖时报告原因，不能声称任意运行均可确定性重放。

## 7. 代码风格与开发习惯

开发友好性优先于抽象技巧。相同职责用相同写法，关键行为能够静态搜索。

- 模块围绕单一 owner 或机制组织。命名描述职责，避免含义模糊的 manager、helper、utils。
- 入口参数、返回值、effect 和错误语义清楚；不以模式开关改变返回类型和生命周期契约。
- 优先直接控制流、组合和显式构造，少用继承、装饰器魔法、动态 import 与隐式注册。
- 数学代码与资源管理代码相邻可追踪，但职责分开；不要把数学拆散进框架回调。
- 注释解释约束、并发顺序和选择原因；public API 文档解释可观察行为及失败条件。
- 错误给出 operation/request/version 等相关身份、违反的约束和失败阶段；避免仅报内部断言，
  也避免吞掉原始异常或将敏感 tensor 内容直接写入错误。
- Formatter、lint、typing 使用仓库统一配置；无关格式化和机械拆文件不混入功能修改。
- 重要架构决策用短记录说明背景、决定、代价及替代方案，不为每个小函数写设计文档。
- 文档只保留一个权威定义，其余链接引用；可运行示例直接复用实际 public path。

## 8. 对 agent 友好的仓库与变更流程

Agent 友好来自局部可理解、边界可验证，而不是增加长篇提示词或放松质量要求。

保留一份短的开发入口，说明架构导航、唯一 authority、环境、构建方式和按变更范围选择的
验证命令。只有确实存在不同约束的子目录才增加局部说明；避免层层指令互相覆盖。

扩展操作应有清楚的最小改动范围：

| 扩展 | 正常修改范围 |
| --- | --- |
| 新算法，使用现有机制 | workload 数学/声明、对应 oracle、示例 |
| 新设备 kernel | provider implementation、capability facts、对应设备边界证据 |
| 新调度策略 | Rust planner 的候选/成本/选择、共用合法性验证及策略实验 |
| 新模型操作 | typed effect/contract、adapter primitive、真实边界证据 |
| 新诊断视图 | 现有 trace 的消费者；确需新事实时才修改生产事件 |

变更过程：先定位 owner 和 observable contract，列出替代对象；针对实际风险选择已有证据或
补一个紧凑反例；实现并删除替代路径；运行相关 gate；记录结果、限制和未完成项。
不得把“测试通过”代替功能完成，也不得为低风险机械修改制造装饰性测试。

工作树和构建产物来源显式可查。验证使用仓库 `.venv`，记录源码 revision、扩展来源、
backend/device 版本与运行命令；不得用另一个 worktree 的旧扩展获得虚假通过。
长任务允许阶段性交接，但每个阶段必须可审查，区分代码存在、静态通过和真实运行通过。
并行开发按 owner 划范围，避免多个开发者同时改公共 schema；不以并行数量衡量进度。

## 9. 系统研究与评价

待验证的命题：显式建模计算修改、状态 effect 与可见性后，可以自动找到正确且高效的安排，
并减少 workload 或资源条件变化后重新手工编排的需要。

多面体、DP、AER 是实现手段。逐项说明它们利用的合法自由度、目标函数、成本事实、适用
结构与求解开销。单纯拥有某个算法名称不构成系统贡献。
实验至少包括认真优化的专用实现、保守合法执行、统一优化执行三者。
变化请求长度、更新频率、状态规模和内存压力；保持算法语义与有效工作量一致。
同时报告延迟分布、吞吐、峰值内存、更新延迟/新鲜度和算法质量，明确静态场景的通用性开销。

支持替换成本模型、调度或表示策略，并复用合法性检查与工作负载。
同一次运行只有一个 authority；研究策略不能通过绕过 effect/version 约束取得收益。
用消融解释机制收益，用失败场景说明边界，不承诺每个场景均优于专家手写实现。

## 10. 分阶段实施与退出条件

1. **选场景、定契约。** 选择能组合学习、发布和条件 replay 的最小算法及 reference，明确
   backend 能力范围和研究假设。退出条件：语义、effect、资源与可见性无歧义。
2. **完成一条可解释路径。** 在现有核心补足必要控制表达与 provenance，执行并定位 reference
   差异。退出条件：数值/状态语义成立，异常和取消正确，来源能追到实际任务。
3. **证明调度价值。** 建立强基线、变化场景和机制消融。退出条件：收益、开销和适用限制有证据。
4. **检验扩展体验。** 由未参与设计的人或 agent 接入一个未预见变体。记录需要修改的 owner、
   阅读范围和遇到的隐含约定；据此改进接口。退出条件：已有能力内不新增专属 runtime 分支。

各阶段复用原计划的 survivor evidence，并保持 TEST_COUNT 上限；新增边界证据需明确计数与
替代关系。保留少量独立 PyTorch reference，不能调用生产实现的同一数学 helper 冒充 oracle。
新能力与替代实现同批收敛，继续记录 SOURCE_LOC 和真实保留职责；预算不够时先重新审视边界，
不能隐藏代码或暗中降低原验收标准。

每个新机制审查五件事：**语义是什么、副作用是什么、谁拥有资源、如何调度、怎样定位错误。**
这些答案应存在于代码和契约的固定位置，不要求每次提交另写五份文档。
最终交付应让算法可表达、系统可研究、GPU 行为可解释、日常扩展可维护。
