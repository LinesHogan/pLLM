# PTTS：给每个请求一块会“长版本”的显存

如果让你在单卡的 Hugging Face 脚本里实现 ESamp——每个请求在生成 token 的同时，在线训练一个 rank-4 的小网络（我们叫它 distiller），用第 0 层的隐藏状态预测最后一层的隐藏状态，采样时再用这个预测去修正 logits——你会怎么管理每个请求的参数？

你大概连想都不用想，顺手就会写下一个 Python 字典：

`states: dict[str, nn.Module] = {}`

新请求进来时，`states[req_id] = copy.deepcopy(template)`，顺手再绑一个 `torch.optim.AdamW`；请求生成结束时，`del states[req_id]`。简单、直观，十行代码搞定。

但在 pLLM 里，当你写下下面这句声明，要求引擎在 128 个并发请求之间同时跑在线训练与采样引导时：

```python
# check-docs: skip: excerpt from README.md
distiller = pllm.RequestState(
    init=pllm.FromModule(
        lambda m: nn.Sequential(nn.Linear(m.hidden_size, 4), nn.Linear(4, m.hidden_size))
    ),
    optimizer=pllm.AdamW(1e-3),
)
```

那个天真的 Python 字典在进入高并发推理引擎的第一秒就会粉身碎骨。接管这句声明的，是 pLLM 底层一套叫做 **PTTS（Paged Tensor Transition System，分页张量状态迁移系统）** 的状态引擎。（顺便提一句，PTTS 开头的 P 是 Paged，即分页与页表，与操作系统的虚拟内存、vLLM 的 PagedAttention 同源；它和 pLLM 名字里代表 programmable 的 p 没有关系，只是碰巧都姓 P。）

为什么存几个小矩阵需要一套专门的“分页张量状态迁移系统”？

因为在一个真正在线上跑满的推理引擎里维护“每个请求自己会变的状态”，你会迎头撞上四起看起来毫无关联的工程事故。如果把它们当成四个独立的 bug，头痛医头、脚痛医脚，补丁只会越打越厚。退后一步看才会意识到：这四个问题在底层问的其实是同一句话，而它们的答案，是系统软件里一个存在了四十年的古老原语。

> **实验环境说明**：文中凡涉及性能与显存实测，除非另有说明，均在单张 NVIDIA RTX 4090（24 GiB）、vLLM 0.32.0（开启 CUDA Graph 与 FlashInfer 采样器）下运行，基座模型为 `Qwen/Qwen2.5-7B-Instruct`（BF16，hidden 维度 3584），并发批量为 128 行（8 个 prompt × `n=16`），每轮生成 256 个 token，取预热后 3 轮中位数。在需要展示小模型上固定调度开销的对比处，会显式标明使用同配置的 `Qwen/Qwen2.5-0.5B-Instruct`。

## 一、 四起看似无关的工程事故

让我们先回到案发现场，看看把可变状态塞进 vLLM 时会发生什么。

**第一起事故：CUDA Graph 的死板地址。**
如果你用 `dict[req_id, nn.Module]` 存状态，128 个请求的小网络就散落在显存的 128 个随机角落里。每一步 decode，哪些请求在批里、排在第几行都在动态变化。但正如我们在[《Python 只在录制时活着》](03-whole-algorithm-in-cuda-graphs.md)里看到的，vLLM 的 decode 步是被录成 CUDA Graph 反复回放的。录像机在录制的那一瞬间，就把每个 kernel 读写的显存指针焊死在了图里。回放时，你可以改指针指向的内存里的数字，但绝不能改指针本身。散落在字典里的张量地址每步都在变，录好的图去哪里找“当前批里第 3 行那个请求的权重”？

在我们的前身系统（旧 tLLM）里，ESamp 用一种叫 **model-bank** 的静态槽数组绕过了这个问题：预先分配固定数量、地址永远不变的槽位，每个槽有自己的 distiller 参数，请求来了借一个槽位，走了还回去。这解决了图的地址绑定，但它没有版本，解决不了后面三起事故。

**第二起事故：双流并发下的读写撕裂。**
在线训练不能串行堵在模型前向的主计算流（`main` stream）上，否则每一步 decode 都要白白多等几百微秒的反向传播和 AdamW 更新。自然的想法是把训练放到一条旁路 CUDA 流（`side` stream）上，让第 $n$ 步的训练和第 $n+1$ 步的模型前向在 GPU 上并行跑。
但如果你只有一块原地修改的 model-bank 槽位，灾难就发生了：当旁路流上的 AdamW 正在往 3 号槽位写第 $n$ 步的新权重时，主流上的第 $n+1$ 步正在从同一个 3 号槽位里读权重来做预测。两边没有任何锁，主流读出来的是一半刚被新梯度冲掉、一半还留着上一步残骸的撕裂参数。

**第三起事故：生成中途的“半句话换脑子”。**
并非所有状态都来自在线训练。有些状态是全局共享或按路由共享的（比如激活引导里的方向向量 `steer`），由外部调用者在发起 `llm.generate(..., batch=pllm.io.StateImport(...))` 时动态推入。假设请求 A 已经生成了一半的句子，此时请求 B 带着一个新的引导向量进来了。如果你直接把新向量覆盖进那个固定的状态槽位，正在说话的请求 A 就会在半句话中间突然被换掉参数，生成出前后精神分裂的文本。

**第四起事故：抢占重算与半途取消。**
在线服务里，显存永远是紧缺的。当 KV cache 被长文本撑爆时，vLLM 的调度器会把某个正在生成的请求临时踢出显存（Preemption），等一会儿有空了，再把它的 prompt 和已经生成的 token 重新送进模型做一遍 prefill，把 KV cache 重建出来。不仅如此，用户还可能在某一步更新刚写了一半时取消请求。
如果状态是原地覆盖的，当一个请求在第 50 步被抢占、不得不退回第 0 步重算 KV 时，它第 0 步时的初始状态早就已经被覆盖得渣都不剩了；如果用第 50 步训练出来的权重去重算第 0 步的 K 和 V，算出来的注意力和被踢走前完全对不上。

## 二、 第一性原理：把时间维度找回来

如果把这四件事当成四个孤立的系统难题来修：给图录制预留固定槽位，给双流并发设计双缓冲，给参数导入加等待队列，给抢占设计状态备份，你会发现，每加一个补丁，它就会和另外三个补丁打架。

为什么会这样？让我们停下来，把业务细节全部剥掉，问一个最赤裸的问题：**这四起事故到底在争抢什么？**

*   CUDA Graph 问的是：在录制时，我怎么用一个固定的地址，去指代运行中不断变化的“当前这一份状态”？
*   双流重叠问的是：当旁路流正在制造“下一份状态”时，主流怎么安全地读取“上一份状态”？
*   外部导入问的是：当新请求换上“新一份状态”时，已经在途的老请求怎么继续持有“它进来时的那一份状态”？
*   抢占与取消问的是：当时间倒流或操作作废时，我怎么回到“准入时的那一份”或“更新前的那一份”？

看出来了吗？这四个问题其实在问完全相同的一句话：

> **在时间线上的任意一刻，某一个读者究竟应该看见状态的哪一份快照？**

只要你的状态模型是“在原地修改同一块显存（In-place Mutation）”，这个问题在数学上就无解。因为原地修改抹杀了时间维度——过去、现在和未提交的未来被粗暴地拍扁在了同一个物理地址里。同一时刻永远只有一份数据，读者和写者、老请求和新请求、正常推进和回滚重算，全都被迫在同一个内存格子里肉搏。

一旦看清这一点，解法根本不需要我们发明。在计算机科学的其它分支里，前人早就用同一个原语把这个问题彻底解决了。

在数据库里，它叫 **MVCC（多版本并发控制，Multi-Version Concurrency Control）**：写事务绝不在原地覆盖数据行，而是生成一个新的行版本；读事务在开始时拿走一个时间戳快照，读的永远是那个时刻之前已提交的版本，读写之间连锁都不用加。

在 Linux 内核里，它叫 **RCU（Read-Copy-Update）**：写者先分配新内存、把旧数据拷过去改好，然后用一个原子操作把新指针发布出去；已经在读旧指针的内核线程继续读它们的，等所有在发布前进入读临界区的读者都退出——这段时间叫“宽限期（Grace Period）”——旧内存才会被安全回收。

如果把 MVCC、RCU 和 vLLM 自己的 PagedAttention 拧在一起，放到 GPU 显存上，会得到什么？

你会得到一条简单得近乎冷酷的铁律：**状态永远是不可变的（Immutable）。**

在 PTTS 里，一份逻辑状态（比如请求 A 的 distiller，我们称之为一条 **Lineage**，即状态谱系）不是一块内存，而是一串单调递增的**不可变版本（Version）**。写者绝不碰任何已经发布的版本；每次更新都是一次**状态迁移（Transition）**——写者申请新的物理槽位，把新参数写进去，写完后原子地发布为下一个版本号；读者在开始工作时钉住（`pin`）某个已发布的版本，在它读完放手之前，这个版本对应的物理显存既不会被任何人修改，也绝不会被回收。

但在 GPU 上落地这套多版本机制，你立刻会撞上两个独特的物理约束：第一，状态可能很大，每次更新都把整个模块复制一遍怎么付得起？第二，GPU 是异步执行的，CPU 上的函数返回了，不代表 GPU 队列里的 kernel 真正跑完了，RCU 的“宽限期”怎么界定？

这就引出了 PTTS 的另外两块基石：**字段级写时复制（Field-level Copy-on-Write）** 与 **CUDA Event 回收栅栏**。

```text
 Version Roots                    Physical Slot Pools (Fixed Base Addresses)
┌─────────────┐                  ┌──────┬──────┬──────┬──────┬──────┐
│ Req A   v7  │──┬──────────────►│Slot 0│Slot 1│Slot 2│Slot 3│ ...  │  Field 0: W1 [cap, 4, H]
└─────────────┘  │   ┌──────────►│ (v7) │      │      │ (v8) │      │
                 │   │           └──────┴──────┴──────┴──────┴──────┘
┌─────────────┐  │   │           ┌──────┬──────┬──────┬──────┬──────┐
│ Req A   v8  │──┼───┘   ┌──────►│Slot 0│Slot 1│Slot 2│Slot 3│ ...  │  Field 1: b1 [cap, 4]
└─────────────┘  └───────┴──────►│(v7/8)│      │      │      │      │
  (W1 updated, b1 shared)        └──────┴──────┴──────┴──────┴──────┘
```

看看上面这张图。一份状态由若干个字段（Field）组成——比如一份带 AdamW 的状态，就是展平的参数 `parameters`、梯度 `gradient`、步数 `step`、一阶矩 `exp_avg`、二阶矩 `exp_avg_sq` 五个字段；图里画的是一份有 `W1`、`b1` 两个字段的状态。在引擎启动的规划期，PTTS 为每个字段预先分配好一块地址永远不变的连续大张量，形状是 `[capacity, *field_shape]`。这就是那个字段的**物理槽池（Slot Pool）**，第 0 维的下标就是槽号（Slot ID）。

那么，一个“版本（Version Root）”在物理上到底是什么？**它仅仅是一组整数槽号——每个字段一个整数。**

当请求 A 的状态处于版本 `v7` 时，它的 `W1` 在 0 号槽，`b1` 也在 0 号槽。现在，某个任务只写 `W1`、不改 `b1`。在准备这次迁移（`prepare_transition`）时，PTTS 只为被修改的 `W1` 分配一个新的空闲槽（比如 3 号槽），而未修改的 `b1` 直接沿用 `v7` 的 0 号槽。这就构成了字段级的写时复制：发布一个新版本的显存与带宽成本，只正比于你**真正动手修改的字段**，而不是整份状态的大小。（在 `handle.diagnostics().state_usage` 里，你会看到 `logical_live_bytes` 和 `allocated_payload_bytes` 两个数字，前者把所有存活版本全算一遍，后者对共享的物理槽只算一次，两者的差值就是字段级 COW 实打实省下的显存。）

那怎么选“页（Page）”的粒度？vLLM 的 PagedAttention 是每 16 个 token 一页，因为 KV cache 是一个 token 接一个 token 往后追加的；但在状态管理里，我们有意识地做了一个更粗暴的选择：**PTTS 的一页，就是一个字段的完整张量。** 为什么不在字段内部再切小块？因为无论是优化器更新还是激活写入，现有的算法几乎都是整个字段一起改，把一个 `[4, 3584]` 的小矩阵再切成碎片，除了徒增页表簿记，换不来半点拷贝节省。与其说它像操作系统里 4 KB 的小页，不如说它是一组带引用计数和版本号的预分配缓冲池（buffers）。

至于 GPU 上的“宽限期”，答案是 **CUDA Event**。当一个写者发布新版本、或者一个读者释放它钉住的旧版本时，对应的物理槽位哪怕引用计数（`holders`）归了零，也不能立刻分给别人用——因为刚才那个读者或写者在 GPU 流上发射的 kernel 可能还在排队。PTTS 会在那条 CUDA 流上打下一个 `torch.cuda.Event` 栅栏（Fence）。宿主机轮询发现这个 Event 已经完成（`event.query() == True`），证明所有触碰过那块内存的 GPU 线程都已经撤离，那个槽位就回到空闲池；实在没有空闲槽时，账本也会把还挂着栅栏的槽位先分出去，但让接手的那条流先在 GPU 上等这个 Event（`stream.wait_event`），旧工作撤离之前新写入不会开始。

## 三、 看一切如何水到渠成

评价一个底层原语好不好，最好的标准不是看它自己有多精巧，而是看当初把你逼入绝境的那几个难题，在它面前是不是全都退化成了平庸的推论（trivial corollaries）。

让我们把前面那四起事故重新放回“不可变版本 + 物理槽池”的透镜下，看看会发生什么。

### 1. CUDA Graph：把指针切换变成整数查表

为什么 CUDA Graph 之前找不到每请求的状态？因为状态散落在动态分配的字典里。
现在，所有字段的物理槽池都是启动时一次性分配好的固定大张量，基地址生老病死都不变。一个版本只是一串槽号。那么，“第 $i$ 行请求在这一步该读哪个版本的状态”，就彻底退化成了一个整数寻址问题：每一步开始前，CPU 把当前批里各行对应的版本槽号填进一张地址同样固定的 `int64` 小表（即 `TableLayout` 的 `sources` 与 `destinations` 段，详见[《Python 只在录制时活着》](03-whole-algorithm-in-cuda-graphs.md)），一次异步拷贝上传到 GPU；录在图里的 kernel 先去表里读出槽号 `slot`，再去池子里取 `pool[slot]`。

版本在变、请求在变，但池子的基地址不变、小表的地址也不变。CUDA Graph 连眼皮都不用抬一下，一套录好的图从头回放到尾。更妙的是，对于像 AdamW 这样需要同时更新参数、梯度、步数和一阶、二阶动量五个字段的操作，我们的分页优化器 kernel（`pllm/kernels/adamw.py`）直接从旧版本的源槽号读取旧参数和动量，在寄存器里算完一步更新后，直接写进新版本的目标槽号——连写时复制的预拷贝都一并省掉了。

### 2. 双流重叠与 `publish_lag`：用一步延迟换取真并发

再看双流并发的读写撕裂。有了不可变版本，主流上的前向读者钉住已发布的旧版本，旁路流上的训练写者往新分配的私有槽位里写新版本，两边物理上碰的根本不是同一块显存，数据竞争自然消失了。

但这里藏着一个更深刻的调度问题：**旁路流写出来的新版本，主流什么时候才能看见？**

如果你用 `pllm.explain` 去查看 ESamp 负载的执行计划，你会看到三行非常有意思的输出：

```text
loss     train           token.commit / side / captured   distiller (latest, 0)
predict  guide_sampling  state.publish / main / captured  distiller (boundary, 1)
timing   publish_lag=1 (default): updates at step n become readable at n + 2; training may overlap later forwards
```

注意 `predict` 后面的 `(boundary, 1)` 和 `timing` 里的 **`publish_lag=1`（默认值）**：第 $n$ 步训练产生的新状态，默认要到第 **$n+2$** 步才会被 `predict` 读到！

很多第一次看到这个默认值的读者会愣住：“为什么不让第 $n+1$ 步立刻用上第 $n$ 步刚训出来的权重？”

让我们把时间线画出来，算一笔简单的物理账。在 ESamp 里，第 $n$ 步的训练任务 `loss` 必须等第 $n$ 步的 token 采样确定（`token.commit` 锚点，即整步的末尾）之后才能启动。它要在旁路流上跑完小网络前向、反向传播和 AdamW 更新。而几乎在 `token.commit` 的同一微秒，主流上的第 $n+1$ 步就已经跨过步边界，准备开始跑模型前向和 `predict` 了。

```text
Main Stream:  [  Step n Forward & Sample  ] ──► [ Step n+1 Forward (reads v_{n-1}) ] ──► [ Step n+2 Forward (reads v_n) ]
                                           \                                            ▲
Side Stream:                                └──► [ Step n Train (reads v_{n-1} -> writes v_n) ]

Active Roots per Lineage during Step n+1 (publish_lag = 1, total = 4 per lineage):
  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
  │ 1. Current   │   │ 2. Private   │   │ 3. Retained  │   │ 4. History   │
  │ Published    │   │ Writing (v_n)│   │ Lag Reader   │   │ Post-Sampler │
  └──────────────┘   └──────────────┘   └──────────────┘   └──────────────┘
```

如果你坚持要求 `publish_lag=0`——即第 $n+1$ 步的 `predict` 必须读到第 $n$ 步训练出的 `v_n`——会发生什么？主流在跨入第 $n+1$ 步时，就必须踩下急刹车，在原地干等旁路流把第 $n$ 步的训练全部跑完。两条流在时间上彻底退化成了串行！

反过来，一旦我们允许哪怕 **1 步的可见性滞后（`publish_lag=1`）**，整条流水线瞬间就活了：
*   当第 $n$ 步的训练在 `side` 流上吭哧吭哧写 `v_n` 时，第 $n+1$ 步的 `main` 流根本不等它，直接钉住第 $n-1$ 步早就发布好的 `v_{n-1}` 往前冲；
*   等第 $n$ 步的训练在后台跑完、把 `v_n` 发布出来，第 $n+2$ 步的 `main` 流自然就能读到 `v_n`；
*   与此同时，训练任务自己读的永远是 `(latest, 0)`——第 $n+1$ 步的训练在 `side` 流上紧跟在第 $n$ 步训练屁股后面，直接在最新的 `v_n` 上继续迭代，**一步梯度都不会丢**。

当然，天下没有免费的午餐。用延迟换并发的代价，是同一时刻显存里必须同时留着好几份版本。到底要预留多少份，才能保证在满负荷流水线下绝不因为槽位耗尽而卡死？

在 `pllm/execution/ptts/page_bundle_planning.py` 里，这个容量规划被浓缩成了短短一行公式：

```python
# check-docs: skip: excerpt from pllm/execution/ptts/page_bundle_planning.py
def version_capacity(lineages: int, publish_lag: int, *, exact_decode: bool = False) -> int:
    # ……
    return (2 if exact_decode else 3 + publish_lag) * lineages + 2
```

不要小看这行简单的算术：`(3 + publish_lag) * lineages + 2`。这里头的每一项，都严丝合缝地对应着状态机里一个真实存在的物理角色：
*   **`1` 份当前已发布根（Current Root）**：谱系当前最新发布的版本；
*   **`1` 份私有写根（Private Root）**：写者正在旁路流上写入、尚未发布的版本；
*   **`1` 份采样后历史根（Retained History）**：主前向跑完到采样结束、移交给旁路训练去读的那份版本；
*   **`publish_lag` 份滞后读者持有的旧根**：因为允许滞后 `lag` 步，主流上的读者还死死钉着 `lag` 步之前的版本不放；
*   **最后 `+ 2` 个翻转槽（Rollover Slots）**：用于步间版本指针原子切换时的周转余量。（如果是像 In-Place TTT 那样在前向内部当场完成读写、不留采样后历史的精确更新 `exact_decode=True`，每个谱系只需要 `1` 份当前 + `1` 份私有写，即 `2 * lineages + 2`；而只读的全局 `InstanceState` 则直接收敛为 `1` 份。）

这里最值得细品的一点是：**为什么公式里没有为“GPU 队列里还没跑完的旧任务”再多预留几份空间？**
因为 GPU 完成栅栏（CUDA Event）已经在管物理复用了！一个版本一旦被新版本取代，只要之前钉住它的读者还在跑，它就正儿八经地占着上面 `(3 + publish_lag)` 里的一个名额；而一旦所有读者都跑完、Event 触发，那个槽位当场就可以被下一个私有写原地复用。逻辑名额和物理生命周期完全闭环，多一分冗余都不需要。

### 3. 在途导入与跨进程共享：锁住你出发时的世界

有了不可变版本，第三起事故——外部参数导入——甚至不需要写任何一行专门的同步代码。

当你在教程 00 的激活引导（`Steering`）里调用 `llm.generate(prompts, batch=pllm.io.StateImport(...))` 时，导入动作无非是在 `steer` 状态上做了一次迁移，发布了一个新版本 `v_new`。这次 `generate` 新准入的请求在进门时调用 `pin_exact`，锁住的是 `v_new`；而五秒钟前就已经进场、此刻正说到半句话的老请求，手里钉住的依然是它进门时的 `v_old`。新老请求在同一个 batch 里并肩跑过第 12 层，各自从同一个槽池的不同槽号里取出自己的引导向量，井水不犯河水。只有当你显式声明 `refresh="step"`（例如实时视频流按步推送帧特征）时，请求才会在每个 decode 步主动换绑到最新发布的那一版。

甚至，这个抽象还顺手免费附赠了一个我们起初根本没奢望过的能力：**同一张 GPU 上的另一个操作系统进程，能不能零拷贝地直接读取推理引擎里的状态？**

在视频会话示例（`examples/video_session.py`）里，独立的视频摄取进程负责解码画面、算出四个特征张量并发布到 PTTS 页池里，然后通过 CUDA IPC 把那个精确版本的只读页句柄借给 LLM worker 子进程。对 PTTS 来说，远在另一个进程的 worker 只不过是又一个握着 `PagePin` 的普通读者——原进程在调用 `release_pin` 时只签发一张释放收据，物理槽位一直静静地留在池子里，直到本地的 CUDA Event 完成、并且远端进程沿着完成通道发回精确的 `close/ACK` 凭证，这块显存才会被回收并推进代次（generation）。无论读者在主线程、旁路流还是另一个进程，“钉住不可变版本，收齐完成凭证后回收”的契约纹丝不动。

### 4. 抢占与取消：当时光倒流时，谁该回到过去？

最后来看第四起事故：操作取消与 vLLM 的抢占重算。

如果一个写者在更新写到一半时报错或被取消，怎么回滚？在原地修改的系统里，你得先备份旧数据再往回拷；而在 PTTS 里，写者本来就在未发布的私有槽位上干活，取消（`abort`）只不过是把那个私有版本直接丢进垃圾桶，已发布的当前版本连一根毫毛都没被碰过。

真正微妙的是 **KV cache 抢占（Preemption）**。当一个请求生成到第 50 个 token 被 vLLM 踢出显存，稍后又从第 0 个 token 开始重新 prefill 这 50 个 token 时，它身上的 PTTS 状态到底应该**保留在第 50 步的最新版本（`keep`）**，还是**倒回它刚进门时的初始版本重头再来（`reset`）**？

如果没有版本模型，你连问这个问题的资格都没有——因为初始版本早就没了。而一旦所有版本都在账本上，答案取决于一个极其清晰的物理分界线：**这份状态到底有没有改动模型算出来的 K 和 V？**

来看看 `pllm/execution/preemption.py` 里的判定函数，全篇只有寥寥数行：

```python
# check-docs: skip: excerpt from pllm/execution/preemption.py
def preemption_policy(attachment: BackendAttachment, sites: tuple[ResidualRewrite, ...]) -> Literal["keep", "reset"]:
    # ……
    return "reset" if applied & _rewritten(graph) or custom or attachment.probe.custom_attention or adaptive else "keep"
```

沿着这条分界线，所有负载被干净利落地一分为二：

第一种情况：**状态只读隐藏层，或者只影响最后的采样器（例如 ESamp 的 distiller）**。
在 ESamp 里，distiller 只是一个挂在模型旁边的“观察员”，它偷看第 0 层和最后一层的 hidden，自己算自己的 loss，只在最后采样时推一把 logits，**从头到尾没有改过 Transformer 内部的任何一个激活值或权重**。这意味着，当 vLLM 把前 50 个 token 重新送进模型重算 KV cache 时，模型算出来的 K 和 V 与被踢走前一模一样！因此，distiller 辛辛苦苦训了 50 步的权重完全应该保留（`keep`）；唯一要注意的是别让那 50 个重算的旧 token 再被送进训练器训第二遍——而这只需要行标签器记住每个请求见过的最大位置游标（`frontier`），把游标之前的重算行直接过滤掉即可（详见[《行模型》](04-packed-rows.md)）。

第二种情况：**状态在运行中被任务改写，并且直接参与了模型前向计算（例如在线更新的参数覆盖层 Overlay、可写残差改写、自定义注意力或自适应跳层）**。
这时候，第 10 步的 K/V 是用版本 `v10` 的权重算出来的，第 20 步的 K/V 是用 `v20` 算出来的。如果你拿着第 50 步的 `v50` 去重算第 0 到 50 步的 K/V，历史就被篡改了。所以策略必须是 `reset`：调用 `rewind_versions`，把该请求的状态指针拨回它准入时锁定的那个初始版本，让状态更新跟着重算的 token 一步步重新演进。

最妙的是这两种情况中间的交集：如果一个适配器或激活补丁（`ActivationPatch`）确实改了模型的残差流，但**它在请求运行期间从来没有被任何内部任务改写过**（比如它是冻结的，或者是在请求第一次前向之前通过 `StateImport` 导入的，即不在 `_rewritten(graph)` 集合里），策略是什么？依然是 **`keep`**！为什么？因为请求从准入那一刻起钉住的就是那个不可变版本，运行中没人改过它，重算时它读到的自然还是同一个版本，算出来的 K/V 分毫不差，连倒回的动作都省了。

## 四、 账本的边界：Python 管对象，Rust 管数字

把“不可变版本 + 字段级槽池 + Event 栅栏”这套原语想清楚之后，工程实现上最大的挑战浮出了水面：**怎么让这套记账逻辑本身足够快，而且绝对不出错？**

在每一步只有几毫秒的 decode 循环里，状态引擎要处理准入分配、写时复制配对、版本发布、精确钉住（pin）、跨流转移以及 Event 轮询回收。早期我们把这套引用计数和字典拷贝全写在 Python 里。有一次我们做性能剖析，拉出来的数字让我们惊出了一身冷汗：每一步 GPU 在显存里真正拷贝状态页（约 6 MB）只花了**十几微秒**，而 CPU 在 Python 里折腾各种版本字典、复制引用集合、扫描回收收据，竟然花了整整 **1.4 毫秒**！

记账的开销比真正干活搬数据贵了一百倍。为什么？因为我们混淆了“控制面的数字事实”与“数据面的设备对象”，还在热路径上干了太多防御性的重复劳动。

那次复盘催生了今天 PTTS 最核心的两个架构决定。

**第一个决定，是在 Python 和 Rust 之间划下一道刀削斧劈的边界：Python 只保管 GPU 对象（字段池的大张量、`torch.cuda.Event` 实例），而所有的数字事实（哪个槽被谁持有、每个槽分配到了第几代、哪些槽在等哪个 Event 编号）全部收归 Rust 账本（`rust/pllm_core/src/page_ledger.rs` 与 `slot_ledger.rs`），两边跨语言边界只传递扁平的 `int64` 数组。**

看看 `slot_ledger.rs` 里一个物理池的账本结构，干净得像教科书：

```rust
#[derive(Default)]
pub(crate) struct Pool {
    pub width: usize,
    pub capacity: usize,
    holders: Vec<i64>,
    generations: Vec<i64>,
    fences: Vec<(i64, Vec<bool>)>,
}
```

这里连一把互斥锁（Mutex）都没有——因为整个状态 Arena 严格归跑模型步的那一个宿主线程单线程拥有。`holders` 是每个槽位的当前持有计数；`fences` 记录着“哪一个 Event ID 完成之前，哪些槽位被禁止复用”；而 `generations`（分配代次）则是我们用来抓野指针的保险丝：每次一个物理槽位被回收再重新分配时，它的代次就加一。如果某段上层代码因为 bug 拿着一个已经释放的旧 `PageSlot` 引用回来取张量，视图检查一比对代次不对，当场就会响亮地抛异常报错，而绝不会悄无声息地读到已经分给另一个请求的脏数据。

在这条边界之上，Python 侧的 `PageBundleArena` 薄得像一层窗户纸。以最核心的 `publish`（发布新版本）和 `abort`（中止私有写）为例，你在 `pllm/execution/ptts/page_bundle.py` 里看到的代码几乎一模一样，只差传给 Rust 账本的最后一个布尔参数：

```python
# check-docs: skip: excerpt from pllm/execution/ptts/page_bundle.py
def publish(self, token: PageWrite) -> PagePublication:
    self._issued_write(token)
    completion = self._record(token.stream)
    completed = self._events.completed()
    retained = self._ledger.publish(token.operation_id, self._events.add(completion), completed, False)
    self._events.retain(retained)
    return PagePublication(token.operation_id, token.before_refs, token.after_refs, completion)

def abort(self, token: PageWrite) -> None:
    """End logical ownership now; future physical reuse waits for the queued writes."""
    self._issued_write(token)
    completion = self._record(token.stream)
    completed = self._events.completed()
    retained = self._ledger.publish(token.operation_id, self._events.add(completion), completed, True)
    self._events.retain(retained)
```

为什么连 `abort`（取消）都非要在 `token.stream` 上记录一个完成事件（`completion = self._record(token.stream)`）并交给账本去立栅栏？

这正是系统程序员最容易踩空的暗礁：**“CPU 上决定取消了”和“GPU 上已经停下了”完全是两码事。** 当你在 Python 里调用 `abort` 的那一刻，这次迁移在**逻辑上**的所有权确实当场终结了，那个私有版本永远不会变成可见版本；但在调用 `abort` 之前，写者可能已经往 `token.stream` 里发射了三四个写内存的 CUDA kernel，它们此刻正排在 GPU 的硬件队列里飞奔！如果你在 `abort` 时不打下 Event 栅栏、直接把那几个私有槽位放回空闲池，下一微秒另一个流上的新请求分到了同一个槽位，就会和还没跑完的废弃写指令迎头相撞。所以，`abort` 和 `publish` 走的是完全相同的物理栅栏回收路径——逻辑上立刻作废，物理上老老实实等 GPU 队列排空。

**第二个决定，是一场无情的“减法审计”。**
我们把 PTTS 在每一步里做的所有动作一条条列在纸上，然后只问一个问题：**PTTS 在物理上到底向系统承诺了哪几条硬保证？**

盘点下来，全部的不变量只有四条：
1. 读者在使用期间，看到的永远是一个固定不变的版本；
2. 写者绝不覆盖任何仍被读者持有的页；
3. 每个状态谱系（Lineage）在同一时刻最多只有一个活跃写者；
4. 一个物理页只有在触碰过它的所有 GPU 读写工作全部完成后，才能被复用。

既然只有这四条，我们就立下了一把审视代码的标尺：**凡是不服务于这四条保证的代码，统统删掉；凡是服务于这四条保证、但不必每一步都做的动作，统统改成惰性或按需执行。**

用这把尺子一量，大把的冗余纷纷落地：
*   以前每次发布版本都要复制整张版本映射字典，现在改成了 Rust 数组里按下标的一次整数赋值；
*   以前每次操作都要挨个轮询并清理所有已完成的收据（`collect_completed`），现在看清了：只要空闲槽还够用，收据留在那儿根本不妨碍任何一条保证！于是回收被彻底改成了**惰性触发**（在 `page_bundle.py` 的 `prepare_transition` 里，只有当 `_ledger.prepare_transition` 抛出 `_core.PageCapacity` 槽位不足异常时，才调用一次 `self.collect_completed()` 去回收已完成的 Event 栅栏，然后再试一次）；
*   以前运行时到处在校验字段 ID 是否合法、状态布局是否匹配，但这些静态事实在引擎启动前的 Rust 规划期早就验过一遍了，运行时热路径上的重复校验全部删光或降级为零成本的 `assert`。

经过这次数组化与减法手术，宿主记账不再是那个 1.4 ms 的大头：后来在 RTX 4090 上剖析 0.5B、$\beta=0$ 的 ESamp，每次调用的中位耗时是 `prepare_transition` 约 **181 µs**，`publish` 约 **82 µs**，`release` 约 **58 µs**。在一步耗时 21.7 ms 的 7B 模型上，这点 CPU 记账时间彻底隐身在了 GPU 计算的阴影之下。

## 五、 物理定律的账单：不可变版本在哪里会疼？

在系统工程里，没有任何一个抽象是免费的。当我们选择用“预分配池 + 字段级 COW + 多版本驻留”来换取无锁并发和 CUDA Graph 兼容时，账单寄到了哪里？

**第一笔账单是显存容量，而且它直接从 KV cache 的嘴里抢食。**
在 vLLM 里，显存分配的先后顺序是铁板钉钉的：先装模型权重，再留 CUDA Graph 捕获池和 pLLM 的状态池，**最后剩下的零头才全部分给 KV cache**。而我们的份数公式告诉我们，为了支持 128 个并发请求在 `publish_lag=1` 下流水线重叠，每个可变请求状态必须预先留出 $4 \times 128 + 2 = \mathbf{514}$ 份（root）的物理槽位。

当状态本身很小的时候，这笔钱花得极其划算。以 Qwen2.5-7B（hidden 维度 3584）上的在线蒸馏为例：由于 pLLM 的自动精度分析（`dtype="auto"`）只把需要被优化器更新的参数和累加器设为 `float32`（防止微小梯度更新在 BF16 的尾数里被吞噬——在 32k token 的长序列递推测试里，FP32 的跨块进位相对误差是 $3.692 \times 10^{-4}$，而 BF16 高达 $1.437 \times 10^{-1}$，差了整整三个数量级），并让只读或只写字段跟随模型的 `bfloat16`，一份完整的 `Distill` 状态（含 rank-4 权重与全套 AdamW 动量）是 $516,176$ 字节（约 504 KiB）。514 份全部预留下来，一共占 **253 MiB**（如果设 `publish_lag=0`，则是 386 份、约 **190 MiB**；至于 `pllm.explain` 指南里那个不带偏置的 `MiniESamp`，每份 458,768 字节，514 份约 **225 MiB**）。在一张 24 GiB 的显卡上，花两百多兆显存买下 128 个并发请求的在线训练与无锁隔离，连眉头都不用皱一下。

但如果你的状态本身是个庞然大物呢？
看看我们在[《参数覆盖层》](06-parameter-overlays.md)里会讲到的 **In-Place TTT**（基于一个 4B 的社区检查点）：它要把选定的 6 层 MLP 下投影矩阵变成每个请求在线更新的“快权重（Fast Weights）”。哪怕用了 `exact_decode` 把份数公式压到了 $2N + 2$，单个请求的一份快权重就重达 **714 MiB**！这意味着哪怕只跑 1 个请求（4 份 root），状态池就要吃掉 **2.8 GiB** 显存；并发开到 4 个请求（10 份 root），将近 7 GiB 的显存就从 KV cache 里蒸发了。

更冷酷的是多卡张量并行（Tensor Parallelism）下的账单。在 pLLM 里，为了严守“扩展层绝不自己发射任何跨卡集合通信（all-reduce / all-gather）”的铁律，PTTS 的状态池在每个 TP rank 上是**完整复制而不分片**的。这意味着当你把 TP 从 1 扩到 4 时，基座模型的权重显存降到了四分之一，但 PTTS 状态占用的显存一分钱都不会少（唯一的例外是走分片证明器的参数覆盖层，我们会在《参数覆盖层》一篇详细拆解）。

**第二笔账单，是模型尺寸对“双流重叠收益”的稀释。**
我们在前面花了很大篇幅解释 `publish_lag=1` 如何让旁路流上的训练与主流上的前向重叠。那么在真刀真枪的基准测试里，这步滞后到底给我们省下了多少时间？

答案可能会让喜欢看漂亮百分比的人清醒一下：**它完全取决于一步训练占一步前向的比例。**

看看我们在同一台 RTX 4090 上，对 0.5B 和 7B 两个模型测出的对比数据（128 并发，ESamp）：

| 模型与配置 | 原生 vLLM 吞吐 (每步耗时) | `publish_lag=0` (串行等待) | `publish_lag=1` (跨步重叠) | 旁路训练每步 GPU 耗时 |
| :--- | :--- | :--- | :--- | :--- |
| **Qwen2.5-0.5B** ($\beta=0$) | 42,355 tok/s (`3.0 ms`) | 38,047 tok/s (**89.8%**) | 38,936 tok/s (**91.9%**) | ~178 µs (AdamW ~29 µs；vLLM 0.27.1 时期的剖析) |
| **Qwen2.5-7B** ($\beta=0$) | 5,887 tok/s (`21.7 ms`) | 5,731 tok/s (**97.2%**) | 5,738 tok/s (**97.4%**) | ~616 µs (AdamW ~191 µs) |
| **Qwen2.5-7B** ($\beta=0.1$) | 5,887 tok/s (`21.7 ms`) | 5,663 tok/s (**96.1%**) | 5,681 tok/s (**96.4%**) | ~616 µs + 引导采样开销 |

在 **0.5B** 模型上，原生 decode 一步只有短短的 **3.0 ms**。这时候，几百微秒的训练和宿主记账在时间轴上占比相当可观，把 `publish_lag` 从 `0` 切到 `1`，吞吐肉眼可见地从 **89.8%** 涨到了 **91.9%**。

但当你换到 **7B** 模型时，原生 decode 一步拉长到了 **21.7 ms**，而 rank-4 小网络的旁路训练一步总共只需要 **616 µs**（其中分页 AdamW 占 191 µs），只占整步时间的 **2.8%**。在 21.7 ms 的汪洋大海里，这 616 µs 无论你是串行等它（97.2%），还是多花 63 MiB 显存用 `publish_lag=1` 把它藏进旁路流里（97.4%），端到端吞吐的差别只有 0.2%，几乎落在了测量噪声的边缘！（我们将在[《自动放置与重叠》](11-automatic-placement-overlap.md)里进一步看到，当 GPU 已经被主干模型吃满时，盲目的双流重叠为什么会变成零和博弈。）

**第三笔账单，是“整字段成页”与“硬容量上限”的刚性边界。**
因为 PTTS 的一页就是整个字段，如果你的算法拥有一张巨大的状态表，但每一步只稀疏地修改其中的一两行，字段级 COW 依然会老老实实地为你分配一整块新字段槽位，并把没改的那几千行原样拷过去——这会带来明显的写放大。同样，因为所有物理槽池必须在录制 CUDA Graph 之前钉死基地址，PTTS 的容量在引擎启动那一刻就是硬上限（Hard Ceiling），运行中绝不会动态调用 `cudaMalloc` 扩容。一旦并发请求加上滞后版本超过了预留槽位数，新请求或者跨步窗口就会直接收到 `WindowBackpressure` 准入拒绝，而不会像操作系统虚拟内存那样平滑地换页到磁盘。

最后，还有一条容易被忽略的语义边界：在 PTTS 里，**“未发布的私有写”和“已发布的版本”隔着一道不可逾越的卢比孔河**。写者在调用 `publish` 之前遇到任何错误，都可以安全地调用 `abort` 扔掉私有页，当成无事发生；但一旦 `publish` 成功返回，新版本就已经暴露给了整个系统，如果在此之后的下游结算步骤发生故障，你绝不能把这次已经发布的更新当成“未提交事务”再重放一遍。同样，跨进程的 `BorrowedPage` 虽然标榜只读，但那只是同一个可信程序内部君子协定式的 API 约束，并不是操作系统页表级别的硬件写保护（`mprotect`）。

同理，如果你拿 PTTS 去和 **S-LoRA** 或 **Punica** 这类多 LoRA 服务系统对比，你会发现它们虽然都借用了“分页（Paging）”这个词，解的却是完全正交的两个问题：S-LoRA 面对的是成千上万个**只读**的预训练 Adapter，它的分页是为了把不同 rank、不同长度的静态权重塞进统一的内存池里防碎片，并用专门的批量异构 GEMM 算子把它们拼在一起算；而 PTTS 面对的是**在服务每一个 token 的过程中都在实时演变、需要并发读写隔离、需要跨流流水线、需要随时回滚的活状态**。

---

## 六、 结语：把并发问题变成记账问题

回过头看，PTTS 之所以长成今天这个样子，几乎是被 GPU 的两条物理定律一步步逼出来的：第一，CUDA Graph 只认固定不变的物理地址；第二，GPU 上的“执行完成”和 CPU 上的“函数返回”隔着一条异步鸿沟。

面对这两条定律，如果你试图在“原地修改状态”的泥潭里用锁、双缓冲和特判补丁去堵漏，你会陷入无穷无尽的竞态条件与死锁里。而一旦你退后一步，承认“状态不可变，每次修改只是发布一串指向固定池子的新槽号”，那四起让你焦头烂额的工程事故——图的地址绑定、双流的读写撕裂、在途请求的隔离、抢占与取消的回滚——瞬间坍缩成了同一个数据结构上的四种简单查询。

这也是我在写完 PTTS 后最大的感触：**在复杂的系统里，当你发现自己正在为三四个看似毫无关联的并发 bug 焦头烂额时，先别急着写第五个补丁。停下来问一句：是不是我们的基础状态模型丢掉了时间维度？**

一旦把时间作为“不可变的版本”显式地请回系统里，原本充满不确定性的并发控制，就变成了一本确定性的、可以用几个平坦的 `int64` 数组算得清清楚楚的账本。记账当然有它的显存代价和繁琐之处，但账本不会说谎，更不会在半夜两点因为两个 CUDA 流的微妙时序差而悄悄算错一个比特。
