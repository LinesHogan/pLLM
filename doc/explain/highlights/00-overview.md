# 给推理引擎装一个“eBPF”：pLLM 为什么存在

如果你做过大模型推理期算法的研究，你一定经历过那种“周日下午的幻觉”。

周日下午三点，你在白板上推出了一个漂亮的想法。比如我们这个项目最早的起点 **ESamp**：大模型在自回归生成时，浅层（比如第 0 层）往往已经能猜出那些烂大街的套话和高频词，而真正深思熟虑的语义要到最后一层才会浮现。如果在生成的每一步，我们都为当前请求在线训练一个极小的秩-4（rank-4）双层网络，让它用第 0 层的隐藏状态（hidden state）去拟合最后一层的隐藏状态；到了采样前，把这个小网络“浅层就能猜出来”的预测从模型的 logits 里扣掉一部分，不就能逼着模型避开陈词滥调、说出更有信息量的话了吗？

在 Hugging Face 的 `generate` 循环里验证这个想法需要多久？大概喝完一杯咖啡的时间。你打开一个 Jupyter Notebook，写一个十几行的 `nn.Sequential`，往第 0 层和最后一层各挂一个 PyTorch 的 `register_forward_hook`，在每步生成后调一次 `loss.backward()` 和 `optimizer.step()`。不到二十行代码，跑通了。

就在这一刻，幻觉产生了：你觉得这个算法已经写完了，距离上线只差“把它搬进 vLLM”。

然后到了周一早上，你打开 vLLM 的源码，试图把那二十行代码塞进去。不到半小时，你就会发现自己像一头撞进了一座高速运转的精密钟表内部——你手里的每一行 PyTorch 代码，都在跟这座钟表的齿轮迎头相撞。

## 一、 十五行代码与五堵物理墙

先把我们要跑的算法摆在桌面上。在今天的 pLLM 里，整个 ESamp 的核心逻辑写出来依然只有十几行：

```python
# check-docs: skip: excerpt from README.md
class ESampLite(pllm.Workload):
    distiller = pllm.RequestState(
        init=pllm.FromModule(
            lambda m: nn.Sequential(nn.Linear(m.hidden_size, 4), nn.Linear(4, m.hidden_size))
        ),
        optimizer=pllm.AdamW(1e-3),
    )

    @pllm.train(state="distiller")
    def loss(self, shallow: torch.Tensor = pllm.hidden(0), deep: torch.Tensor = pllm.hidden(-1),
             f: nn.Module = pllm.module("distiller")) -> torch.Tensor:
        return (f(shallow) - deep).square().mean(-1)

    @pllm.guide_sampling(beta=0.5)
    def predict(self, shallow: torch.Tensor = pllm.hidden(0), f: nn.Module = pllm.module("distiller")) -> torch.Tensor:
        return f(shallow)
```

看着几乎和你在 Notebook 里写的原型一模一样，对吧？但如果你不用扩展层，而是试着把同样逻辑的原生 PyTorch hook 直接塞进 vLLM，你会接连撞上五堵结结实实的墙。

> **实验基线声明**：除非另有说明，本文及本系列引用的实测数据均基于同一套基线环境——单张 NVIDIA RTX 4090（24 GiB）、vLLM 0.32.0（PyTorch 2.13.0+cu129，开启 CUDA Graph 与 FlashInfer 采样器），基座模型为 **Qwen2.5-7B-Instruct（BF16）**，并发负载为 8 条 prompt × 每条采样 $n=16$（共 128 个并发序列），每条生成 256 个 token，预热 1 轮后取 3 轮中位数。在需要展示固定调度底噪对小模型的影响时，我们会对照完全相同配置下的 **Qwen2.5-0.5B-Instruct**。

### 第一堵墙：连续批处理抹掉了“谁是谁”

在研究脚本里，张量是三维的 `[batch_size, seq_len, hidden_size]`。第 0 号请求永远住在 `hidden[0]`，门牌号清清楚楚。

但在生产级服务引擎里，为了不让短请求干等长请求、也不让刚进来的请求在门外排队，vLLM 采用的是**连续批处理（Continuous Batching）**与**分块预填充（Chunked Prefill）**。在同一步（engine step）里，引擎会把几十个正在吐字的解码（decode）请求（每个请求 1 个 token）和几个刚进门、正在分段消化的长 prompt 请求（每个请求几百个 token）首尾相接，拍扁成一张紧缩的二维张量 `[num_tokens, hidden_size]`。

```text
研究脚本里的世界 (Hugging Face):             生产引擎里的世界 (vLLM Continuous Batching):
┌───────────────────────────┐               ┌───────────────────────────────────┐
│ Req A: [t0, t1, t2, pad]  │               │ Row 0:    Req B (decode, tok #41) │
├───────────────────────────┤               │ Row 1..4: Req C (prefill chunk)   │
│ Req B: [t0, t1, pad, pad] │      ──►      │ Row 5:    Req A (decode, tok #12) │
└───────────────────────────┘               │ Row 6..7: Graph Padding (幽灵行)   │
  形状规整 [B, S, H]，身份固定                 └───────────────────────────────────┘
                                              扁平张量 [N, H]，每步洗牌，没有户口本
```

当你的 forward hook 在第 0 层被唤醒时，递到你手里的只有这张光秃秃的 `[num_tokens, hidden_size]` 二维张量。哪一行属于张三的请求？哪几行是李四还没算完的半截 prompt？张量末尾甚至还塞着几行为了凑齐硬件图尺寸而填进去的“幽灵 padding 行”。更要命的是，下一步再进来时，有老请求结束退出，有新请求插队进来，还有请求因为 KV 显存不够被临时**抢占（Preempt）**踢出局、稍后从头重算——调度器在每一步都会重新洗牌，所有人的行号全变了。

### 第二堵墙：CUDA Graph 让你的 Python 代码人间蒸发

好，就算你历尽千辛万苦，在 Python 里通过读引擎内部变量搞清楚了每一行是谁。当你启动服务，跑起 decode 阶段时，你会发现一件更诡异的事：**你的 Python hook 根本没有被调用。**

为什么？算一笔简单的延迟账就明白了。

在自回归 decode 阶段，每个请求每一步只生成 1 个 token。对于 0.5B 这样的小模型，128 个并发序列在 RTX 4090 上跑完一整步前向加采样，总共只需要 **3.0 ms**（吞吐约 42,355 tok/s）。而在一个 24 层或 28 层的 Transformer 里，一步前向包含几百个细碎的 GPU 算子（kernel）。如果让 Python 解释器在每一步里经过 PyTorch 调度器、再调 CUDA Driver 去一个个发射这些算子，CPU 发射一次就要花掉几微秒——GPU 算得比 CPU 喊口令还快，绝大部分时间 GPU 都在干等 CPU 派活！

为了砍掉这笔 CPU 发射税，vLLM 会把整个 decode 步录制成一张 **CUDA Graph**。录制（Capture）只在启动时发生一次：CPU 像平时一样跑一遍 Python 前向代码，但 GPU 并不真的去算数据，而是把“调用了哪些 kernel、每个 kernel 的网格多大、读写了哪几个显存地址”原封不动地录成一张静态的指令图。到了真正的线上服务期，每来一步 decode，CPU 只需要发出一道指令：“把刚才那盘磁带重放（Replay）一遍！”

在磁带重放期间，GPU 自己顺着录好的图一路狂奔，**Python 解释器根本不参与层的执行**。你写在 Python hook 里的 `if/else`、字典查找、动态分配，在录制完的那一刻起就已经死掉了。如果为了迁就你的 hook 而强行关掉 CUDA Graph 退回 eager 模式，代价有多惨烈？在 0.5B 模型上，单步耗时直接从 3.0 ms 暴涨到 6.1 ms，吞吐跌到 20,926 tok/s——**整整腰斩了一半（只剩图模式的 49%）**。即便在单步计算重达 21.7 ms 的 7B 模型上（原生图模式 5,887 tok/s，关掉图仍有 5,773 tok/s，约 98%），一旦你的扩展自己要在每步里跑包含反向传播与 AdamW 更新的几十个小算子，不进图同样要为每个小算子付一次 CPU 发射开销。

而且，CUDA Graph 还有一条冷酷的物理铁律：**录进图里的每一个算子，只认录制那一刻绑定的固定显存地址（Pointer）和固定张量形状。** 只要你在下一步里 `torch.empty()` 新分配了一块张量，图回放就会对它视而不见，依然去敲录制时的旧地址。

### 第三堵墙：每请求的状态无处安放

在 ESamp 里，每个请求都有自己独立的 `distiller` 权重，外加 `AdamW` 优化器的一阶动量 `m`、二阶动量 `v` 和步数计数。

在并发服务里，这意味着：
1. 状态必须跟着请求的生命周期走——请求进门时初始化，生成结束时立刻回收显存；
2. 状态的地址必须在 CUDA Graph 里保持绝对固定——不能因为请求 A 走了、请求 B 来了，就重新录一遍图；
3. **读写不能在同一个地址上打架**——当旁路流（side stream）上的优化器正在为第 $n$ 步更新某请求的权重时，主流（main stream）上的第 $n+1$ 步前向可能已经开始读取这个请求的权重了。如果在原地直接改写（in-place mutation），主流就会读到写了一半的撕裂张量。

### 第四堵墙：额外的计算与主流水线争抢预算

在研究脚本里，多算一个辅助 loss、多跑一次小网络，无非是实验从 10 分钟变成 12 分钟。但在高并发服务引擎里，**显存和流时间是严格零和的**。

先看显存的分配食物链：一张 24 GiB 的显卡，要先装下模型权重，再划走 CUDA Graph 的静态显存池和扩展自己的状态缓冲，**最后剩下的边角料，才全部交给 KV Cache**。KV Cache 的大小直接决定了引擎能同时容纳多少个并发请求。有一次在 7B 模型上，我们为了录下更大的模型图，把捕获上限强行拉到 8,192 个 token，结果模型图池子一口吃掉了大块显存，留给 KV Cache 的空间从 76,144 个 token 断崖式暴跌到 3,872 个，并发上不去，最终吞吐跌得只剩原生的 **21%**（历史测量）。

再看时间线与主机同步（Host Sync）。如果你把在线训练串行塞进主计算流，每一步平白多出几百微秒，吞吐立刻掉一截；如果你想用多条 CUDA Stream 做异步重叠，你就得自己和流同步事件、SM 硬件槽位抢占搏斗。更致命的是 PyTorch 用户习以为常的 `.item()`、`print(tensor)` 或 `if tensor.norm() > 1:`——哪怕整步里只有**一次**这样的调用，CPU 都必须停下脚步，干等 GPU 把队列里积压的所有算子全部排空，把那几个字节跨过 PCIe 传回主机内存。我们在早期优化 ESamp 时吃过一次刻骨铭心的亏：把每步的 CPU-GPU 同步减掉几次，吞吐几乎纹丝不动；只有当同步次数真正变成**零**的那一刻，图模式的吞吐才瞬间从 11.6k 跳到了 19.1k tok/s（0.5B 历史测量）。

### 第五堵墙：改动模型内部结构等于拆引擎

如果你的算法不止满足于在模型外围读个 hidden，而是想改写某一层的残差连接（比如超连接 Hyper-Connections）、给线性层叠加上每个请求自己的快权重增量（比如 In-Place TTT）、让部分 token 在深层提前早退（Early Exit），或者干脆把偶数层的注意力换成只保留最近 256 个 token 的滑动窗口呢？

在今天的推理引擎里，模型前向被 `torch.compile`（Dynamo + Inductor）编成了分段计算图，残差加法被吞进了下一层的 `fused_add_rms_norm` C++ 内核里，而注意力算子与底层的 PagedAttention 块表管理器死死咬合在一起。想改它们？你唯一的出路就是 `git clone` 一份 vLLM 源码，在 `GPUModelRunner` 和底层算子里直接动刀。

## 二、 历史的回响：当年的 Linux 是怎么走出死胡同的？

当你把这五堵墙并排画在白板上，退后两步端详时，一件非常有意思的事情浮现了出来：

**这五堵墙里，没有哪怕一堵是机器学习问题。它们全都是纯粹的系统问题。**

而且，这不是一个新问题。过去三四年里，大模型领域奉行的是萨顿（Richard Sutton）《苦涩的教训》的极简主义——所有任务统一成最干净的 Transformer 前向，靠堆算力和数据解决一切。但随着摩尔定律放缓、单 token 推理成本被极限挤压，研究界和工业界正在不可避免地走向一个“更脏、更有状态、更依赖测试期计算与结构先验”的新阶段：有人在 decode 时在线蒸馏（ESamp），有人在上下文里实时做梯度下降更新快权重（TTT），有人挂接巨大的 n-gram 外部记忆表（Engram），有人按层跳过冗余计算，有人动态干预激活与采样分布。

所有这些五花八门的新算法，在面对 vLLM 这样的底层推理引擎时，其实都在问同一个古老的系统工程问题：

> **当你面对一个为了榨干硬件性能而高度静态化、同时服务成百上千个租户的底层引擎时，怎么允许外部开发者在里面安全、高效地运行一段有状态的自定义程序，而不用每次都把引擎拆开重装？**

在系统软件的历史上，这条路我们已经完完整整地走过一次了。

在 eBPF 出现之前，如果你想在 Linux 内核的网络栈里做超出简单过滤的自定义包处理，或者在系统调用入口做细粒度的性能追踪，你只有两个糟糕透顶的选择：
*   **选择一：把数据包全部拷回用户态（User Space）处理。** 在用户态写代码惬意、安全，随便你怎么分配内存、怎么写分支。但上下文切换和内存拷贝的开销会把万兆网卡的吞吐吃得渣都不剩。
*   **选择二：自己写一个 Linux 内核模块（Kernel Module）。** 你可以直接挂进内核函数指针，拿到裸金属般的速度。代价是什么？代价是一个越界指针、一次忘记释放的锁，就能让整台物理服务器当场 Kernel Panic；而且内核内部结构体稍微一升级，你维护的内核模块就得推倒重改。

看看今天的大模型推理生态，像不像 eBPF 出现之前的 Linux？

研究者在 Hugging Face、TransformerLens 或 nnsight 里用 Python hook 写原型，就像在用户态写脚本：极其顺手，但没有连续批处理、没有 CUDA Graph，慢得根本上不了生产；而一旦要上生产，算法工程师就只能 fork 一份 vLLM 源码，为每个算法拉一个专属分支——这就是在写内核模块。每个算法自己去排抢占、并发隔离、显存碎片和流同步的雷；等到 vLLM 上游发一个新版本，所有人一起痛苦地解几千行代码冲突。至于 vLLM 原生提供的扩展点，无论是只能改最终词表得分的 `LogitsProcessor`，还是形态固定的只读 Multi-LoRA，都远不足以表达“在模型内部任意层读写、跨步维护可变状态、在图内在线训练”的通用逻辑。

Linux 最终是怎么终结“要么慢死在用户态、要么撞死在内核模块”的二选一困境的？

答案是 **eBPF**。

eBPF 没有给用户发一把可以随便捅破内核的瑞士军刀，而是立下了一套极其克制、却足以拼出万千变化的**五件套契约**：

1.  **Verifier（验证器）**：程序在装入内核之前，必须先过一道静态检查关。验证器确保你的代码不会死循环、不会越界访问别人的内存、不会在禁止睡眠的上下文里阻塞。不合规的程序在门外就被直接拒之门外（Fail-Closed）。
2.  **JIT 编译器**：一旦通过验证，受限的字节码会被直接编译成宿主机原生机器码，以零解释器开销在内核态全速奔跑。
3.  **BPF Maps（受管状态）**：eBPF 程序本身不直接 `kmalloc` 裸内存，所有跨调用存活的状态都必须存放在内核统一管理的键值对或数组（Maps）里，由内核负责并发安全与生命周期回收。
4.  **Attach Points（挂载点）**：你不能随便改写内核的任意一行指令，只能在明确定义的静态或动态锚点（如 XDP、tc、kprobe、tracepoint）上挂载逻辑。
5.  **Observability（可观测性）**：配套的 `bpftool`、`perf` 与 `bpftrace` 让你在运行前后清晰地看清程序的资源占用与执行耗时。

当我们意识到“把推理时算法放进 vLLM”本质上就是在“给推理引擎装一个 eBPF”时，pLLM 的整个架构版图瞬间清晰了。我们不需要去造一个无所不能的动态 Python 魔法盒，我们需要造的，正是推理引擎里的这五件套：

| Linux eBPF 组件 | pLLM 中的对应原语 | 核心职责与设计机制 | 深入剖析的篇章 |
| :--- | :--- | :--- | :--- |
| **Verifier**（装载前验证） | **声明反射 + Rust 规划 + `pllm.testing.check`** | 用 `meta` 张量静态拦截 `.item()` 同步与非法依赖；在 CPU 上用固定调度做蜕变测试，检验请求隔离、行置换不变性与抢占重算一致性 | [第 12 篇：信任用户程序](02-trusting-user-programs.md) |

*（顺带一提，PTTS 是 Paged Tensor Transition System 的缩写。它开头的 P 指的是 **Paged**——即像操作系统虚拟内存和 vLLM 的 PagedAttention 那样做分页与页表映射；和 pLLM 名字里的 p（programmable，可编程）没有任何血缘关系，纯粹是碰巧撞了首字母。）*

当然，任何系统类比都有它的边界，坦诚地划清边界比生搬硬套更重要：
*   **第一，验证的强度不同。** eBPF 的 verifier 面对的是没有任意指针算术的受限字节码，它给出的是数学意义上的**形式化证明**；而 pLLM 面对的是图灵完备的 Python 与庞大复杂的 PyTorch 算子库，要形式化证明一段任意张量代码“绝不在第 0 维上串行（mix rows）”是不现实的。因此，pLLM 采取的是“静态形状/同步拦截 + 确定性调度下的加盐差分测试（Metamorphic Testing）”——它不是数学证明，但足以在装载前揪出常见的跨请求污染和抢占 bug。
*   **第二，负载的体量不同。** eBPF 程序通常是几百条指令的轻量探针；而 pLLM 的负载可以在旁路流上跑完整的反向传播与 `AdamW`，可以跨 PCIe 异步预取几个 GiB 的主机查找表，甚至可以接管整座模型的层间循环。
*   **第三，宿主接口的稳定性不同。** Linux 的 tracepoint 和 kprobe 有内核社区维护的契约；而 vLLM 正处在极速演进期，内部结构每隔几个月就会大改。pLLM 没有奢望上游为你冻结内部类，而是选择将 vLLM 0.27.1 与 0.32.0 的内部差异集中关在 `pllm/backends/vllm/compat.py` 这一个隔离舱里（另有少数几处按它导出的版本开关分支），对外提供稳定的声明接口。

## 三、 两大基石：声明代替 Hook，以及“一张 `int64` 小表”

明确了“我们要造一个推理引擎的 eBPF”，接下来的问题是：在工程机制上，到底靠什么把高度动态的“每请求、每步变化、多版本状态”塞进高度静态的 CUDA Graph 里？

在这个系列的十二篇文章里，你会看到各种各样的编译器手术与内核技巧，但所有技巧往下挖三尺，都立在两块共同的基石之上。

### 基石一：只声明“本质语义”，用一次 Meta 追踪代替运行时回调

为什么传统的 PyTorch hook 进不了生产引擎？因为 hook 把**“算法想算什么数学”**和**“引擎该在什么时候、怎么搬运张量”**死死搅在了一起。

回看文章开头的 `ESampLite`。在设计 pLLM 的接口时，我们反复问自己一个问题：剥掉所有底层引擎的机械噪音（什么页表槽位、CUDA 流同步屏障、行打包拆包、版本引用计数），一个算法设计者**最少只需要告诉系统哪几件事**？

答案只有四件：
1.  **状态的作用域与生命周期**：这个张量是全实例共享（`InstanceState`），还是每个请求独占一份（`RequestState`）？怎么初始化？用什么优化器？
2.  **读取什么输入**：写在方法参数的默认值标记上——比如 `shallow: torch.Tensor = pllm.hidden(0)`、`f: nn.Module = pllm.module("distiller")`。
3.  **产生什么效果与时机**：写在方法装饰器或模型声明上——比如 `@pllm.train(state="distiller")`、`@pllm.guide_sampling(beta=0.5)`。
4.  **纯粹的张量数学**：方法体内部只写干干净净的 `(f(shallow) - deep).square().mean(-1)`，假定第 0 维永远是对齐好的活跃请求行。

因为输入、状态和效果全部是声明式的，pLLM 根本不需要等到运行时才去猜你的代码干了什么。在引擎启动前（或者当你在笔记本电脑上调用 `pllm.explain` 时），框架只需在 CPU 上构造一批只有形状、没有实际内存数据的 PyTorch **`meta` 张量**，把你的方法调用一次。

这一遍毫无开销的“空跑”，就像给代码照了一次 X 光：
*   如果你在代码里写了 `.item()` 或 `if h.norm() > 1:`，因为 `meta` 张量没有数值，追踪当场就会失败并报错，帮你把破坏 CUDA Graph 和引起主机同步的毒药拦在门外；
*   框架顺着 `meta` 张量的计算图，一次性提取出每个方法读了哪一层、写了哪份状态、中间激活占了多少字节、产生了多少 FLOPs；
*   随后，这张带类型的语义图（`SemanticGraph`）通过 FFI 交给 `rust/pllm_core/src` 下约 4,300 行 Rust 编写的规划器，由 Rust 推导出数据依赖、选择执行时间轴锚点与 CUDA 流车道、在显存预算内为每份状态选定存储方案，最终签发出一份不可篡改的物理计划（`PhysicalPlan`），交给 `pllm/` 下约 4 万行 Python 的运行时与 PTTS 显存池去执行。

### 基石二：CPU 每步算好一张 `int64` 小表，GPU 按表索骥

有了物理计划，我们终于来到了最核心的矛盾面前：**CUDA Graph 只认死板的固定显存地址，而连续批处理里的请求行号、每个请求当前读写的页表槽位、甚至外部张量的内存指针，每一步都在变。这两件事怎么同时成立？**

答案是系统设计里最古老、也最优雅的那招：**加一层间接（Indirection）——把所有会变的“结构与控制流”，统统编码成一张固定地址的 `int64` 整数表里的“数据”。**

在 pLLM 中，所有每请求的状态张量都预先分配在一块容量固定、地址永不改变的分页显存池（PageBundle Arena）里。除此之外，我们还在显存里划出了一张地址同样永远固定的共享 `int64` 小表。在 `pllm/execution/tensor_executor.py` 中，`TableLayout` 的注释把这张表的四段结构写得一目了然：

```python
# check-docs: skip: excerpt from pllm/execution/tensor_executor.py
@dataclass(frozen=True, slots=True)
class TableLayout:
    """One resource's segments in the shared int64 table, uploaded in one copy per step.

    rows          [6, R]   per row: sampler row, sample index, state (S: padding sink), version, packed row, active
    sources       [F, S+1] source page slot per field and state (-1: none)
    destinations  [F, S]   destination page slot per field and state (-1: do not write)
    row inputs    [K, 3]   address and strides of each token or sampler tensor
    """
```

让我们把这张表画出来，看看它是怎么把 CPU 的灵活性和 GPU 图的静态性缝合在一起的：

```text
CPU (每步在锁页内存 Pinned Memory 中填数)                GPU (地址焊死的 CUDA Graph 回放)
┌──────────────────────────────────────────┐          ┌──────────────────────────────────────────┐
│ Shared int64 Table (固定设备地址 0x7f00..)│  1次异步  │ 录好的 Kernel 只认 0x7f00.. 这个门牌号：  │
│ ──────────────────────────────────────── │  H2D拷贝  │                                          │
│ 1. rows [6, R]:                          │ ───────► │ • 查 rows + sources:                     │
│    行 r 属于哪个请求 state? 在扁平 batch   │ (几微秒)  │   去状态池的哪个物理页槽读当前版本参数？    │
│    的哪一行? 是否有效(active)? (无效指到S) │          │   (填充行自动路由到全 0 的哑状态槽 S)       │
│ 2. sources [F, S+1]:                     │          │ • 查 destinations:                       │
│    每个请求的第 f 个字段，这步读哪一页？    │          │   算完的新权重/动量写进哪个新分配的页槽？   │
│ 3. destinations [F, S]:                  │          │ • 查 row inputs:                         │
│    写状态的方法，这步把新版本写到哪一页？   │          │   把 64 位整数强转回设备指针 tl.pointer_type│
│ 4. row inputs [K, 3]:                    │          │   去读 vLLM 刚刚动态分配的外部张量！        │
│    外部张量这步的裸地址 data_ptr 与步长     │          │                                          │
└──────────────────────────────────────────┘          └──────────────────────────────────────────┘
```

仔细体会一下这张表里的精妙之处：

*   **怎么处理每步请求数的变化？** 图是按最大容量 $R$ 录制的。如果这一步只有 5 个活跃请求，剩下 $R-5$ 行怎么办？CPU 在填表时，把那 $R-5$ 行的状态编号填成 `S`（即表里的第 $S+1$ 列，一个权重永远为 0 的**哑状态槽 Padding Sink**），同时把 `active` 填成 `0`。GPU 按图索骥，5 个真请求算真梯度，填充行在哑槽上空转并被 `active` 掩码在设备端直接清零——既不用重录不同尺寸的图，也不会污染真请求的梯度。
*   **怎么处理多版本状态的并发读写？** 读方法看 `sources` 段，写方法看 `destinations` 段。CPU 的 PTTS 页表管理器在每步开始前，让主流的前向在 `sources` 里指向上一步已经发布好的旧版本页槽（比如 0 号槽），同时在 `destinations` 里为旁路流的优化器分配一个空闲的新页槽（比如 3 号槽）。两条流各自对着固定地址的表做间接寻址，物理上读写完全不同的显存页，连锁都不用加。
*   **甚至连 vLLM 每步动态搬家的外部张量，也能塞进表里！** 采样器传过来的某些张量归 vLLM 自己管，每一步的显存地址都在变。我们就让 CPU 每步调一次 `tensor.data_ptr()`，把拿到的 64 位裸内存地址连同两个步长（strides）当作三个普通的 `int64` 填进表的第 4 段 `row inputs` 里；到了 GPU 的 Triton kernel 内部，直接把这个 `int64` 整数强转回硬件指针去解引用。

这张小小的 `int64` 表，是整个系列的“母题（Motif）”。你会在[第 1 篇（行模型）](04-packed-rows.md)里看到它的 `rows` 段是怎么从 vLLM 入口的三个整数推出来的；在[第 2 篇（CUDA Graph）](03-whole-algorithm-in-cuda-graphs.md)里看到它怎么把整步反向传播和 AdamW 塞进图里；在[第 3 篇（PTTS）](01-ptts.md)里看到 `sources` 和 `destinations` 怎么驱动写时复制与版本变迁；甚至在[第 4 篇（图内挂载点）](05-in-graph-attach-points.md)和[第 5 篇（参数覆盖层）](06-parameter-overlays.md)里，你会看到这张表的**内存地址本身**被当成了跨过 PyTorch 编译器结界的“会话身份证”。

## 四、 一步 Decode 的时空全局图与真实代价

当“声明式契约”与“一张 `int64` 小表”结合在一起，一步大模型解码在时间与空间上就变成了一座精密咬合的流水线。

为了看清后面十二篇文章各自站在整个系统的哪个位置，我们把 pLLM 中一步 decode 的主要**时间轴锚点（Anchors）**和两条 **CUDA 流车道（Main / Side Lanes）** 展开在下面这张图上：

```text
时间轴锚点:  request.prepare    model.execute        state.publish    sampler.pre_draw  token.commit      next.prepare
                 │                  │                    │                 │                 │                 │
                 ▼                  ▼                    ▼                 ▼                 ▼                 ▼
第 n 步   main:  ├── [01:算行标签] ──┼── [04:图内改残差] ──┼── [predict] ────┼── [09:采样尾声] ─┤                 │
(主流)           │   (填表上传H2D)   │   [05:参数覆盖层]   │   (读 lag=1 版本)│   (三遍扫描融合)  │                 │
                 │                  │   [06:自定义层循环] │                 │                 │                 │
                 │                  │   [07:自定义注意力] │                 │                 │                 │
                 │                  │                    │                 │                 │                 │
          side:  ├── [10:主机查表] ──┼────────────────────┘                 │                 ├── [02:整步训练] ──┼──────┐
(旁路流)         │   (1/4 SM 限流， │                                      │                 │   (loss反向+AdamW │      │
                 │    与前向重叠)    │                                      │                 │    写新页槽，与   │      │
                 │                                                         │                 │    n+1步前向重叠) │      │
第 n+1 步 main:  │                                                         │                 ├── [准备 n+1] ───┼── [模型前向 n+1] ──►
                                                                                                               ▲      │
                                                                                              [03:PTTS 在边界发布版本]─┘
                                                                                  [11:自动放置求解锚点窗口与跨步 lag=1]
```

顺着这张时间线从左往右看，你会发现前面提到的所有棘手约束，都变成了时间轴上的几何排布问题：

*   在 `request.prepare`，CPU 拦截 vLLM 的输入批次，瞬间算出每一行属于哪个请求，填好 `int64` 表异步推上 GPU（[第 1 篇](04-packed-rows.md)）；如果你的算法需要去主机内存里查几百兆的外部记忆表，旁路流（`side`）此时立刻启动一个只占 1/4 SM 的持久化 kernel，趁着主流跑模型前向的空档把数据跨 PCIe 偷偷搬完（[第 10 篇](12-bounded-zero-copy-gather.md)）。
*   在 `model.execute` 内部，模型顺着 CUDA Graph 飞奔。图内挂载点在不拆散原生融合算子的前提下改写残差（[第 4 篇](05-in-graph-attach-points.md)）、叠加上每请求的参数覆盖层（[第 5 篇](06-parameter-overlays.md)）、按掩码跳过深层（[第 6 篇](10-custom-layer-loops.md)）或切换自定义的注意力与 KV 布局（[第 7 篇](08-programmable-attention-kv.md)、[第 8 篇](09-reusing-upstream-kernels.md)）。
*   到了 `state.publish` 与 `sampler.pre_draw`，前向激活就绪，引导方法 `predict` 算出浅层预测，直接融合进采样器原本就有的词表扫描尾声里，绝不额外多扫一遍 15 万词的大词表（[第 9 篇](07-sampler-epilogue.md)）。
*   在 `token.commit` 采样落定之后，本步抽出的 token 诞生。在线训练任务 `loss` 在旁路流上启动（[第 2 篇](03-whole-algorithm-in-cuda-graphs.md)），一边算反向传播和 `AdamW`，主流一边头也不回地进入第 $n+1$ 步的前向。

你可能会问：等等，第 $n$ 步的训练还在旁路流上跑，第 $n+1$ 步的主流前向就已经开始了，那第 $n+1$ 步的 `predict` 读到的是什么权重？

这就是我们在系统层面做出的一个关键交换——默认 **`publish_lag=1`**（[第 3 篇](01-ptts.md)与[第 11 篇](11-automatic-placement-overlap.md)）。第 $n$ 步算出的参数更新，默认在第 **$n+2$** 步才对其他读取者可见；第 $n+1$ 步的主流直接读取第 $n-1$ 步早已发布好的不可变版本（而训练任务自己始终基于最新参数继续迭代，一步梯度也不丢）。用“可见性晚一步”的微小算法代价，换取了主流前向与旁路训练的彻底解耦与并行（如果你的算法在数学上要求严格无滞后，也可以显式设 `publish_lag=0`，主动用吞吐换严格步序）。

### 账本的背面：我们付出了什么代价？

没有哪套系统抽象是免费的。把扩展层建立在“静态追踪 + 固定地址表 + 版本化分页池”之上，意味着我们必须在两个地方付出实打实的代价。

**第一个代价是固定底噪（Fixed Overhead）。**
每一步在 CPU 上维护页表、上传几千字节的 `int64` 表、发射旁路流事件以及运行几个零碎的 gather/scatter kernel，加起来有几十到几百微秒的固定成本。
*   在 **7B 模型**上，原生 vLLM 跑一步 decode 本来就要 **21.7 ms**（5,887 tok/s）。几百微秒的底噪加上旁路训练完全淹没在漫长的矩阵乘法里：跑 ESamp 只训练不引导（$\beta=0$）时吞吐是 **5,738 tok/s（原生的 97.4%）**，同时开启训练与对比引导（$\beta=0.5$）时是 **5,678 tok/s（原生的 96.3%）**（在 A100-SXM4-80GB 多卡环境下，7B $\beta=0$ 在 TP=1/2/4 下也分别保持在原生的 95.84%、95.63% 和 97.60%）。
*   但在 **0.5B 小模型**上，原生一步总共只有 **3.0 ms**（42,355 tok/s）。这时候，那几百微秒的固定底噪就再也藏不住了：同样跑 ESamp，$\beta=0$ 时吞吐掉到了 **38,936 tok/s（原生的 91.9%）**，而在早先 vLLM 0.27.1 上做的 20 轮交叉测量里，$\beta=0$ 是 92.45%，加上采样引导（$\beta=0.5$）后更是掉到了 **83.38%**。

我们从不讳言这个数字：**这套架构在 0.5B 这样极小的模型上有 8%–17% 的可见吞吐开销；模型越大、单步计算越重，相对开销就越薄，到 7B 规模时收敛在 3%–4% 左右。**

**第二个代价是表达边界（Expressive Boundaries）。**
为了守住连续批处理的隔离性与 CUDA Graph 的静态性，有些在单请求脚本里随手就能写的算法，在 pLLM 里会被构建期检查直接举红牌拦下：
*   你不能写跨行归约（如 `h - h.mean(dim=0)`）或批次内竞争路由（Expert-Choice MoD），因为那会让张三的回答取决于这一毫秒刚好和谁拼在同一个 batch 里；
*   你不能实现像 SnapKV、H2O 那样“根据运行时注意力分数动态释放序列中间某个 token 的物理 KV 显存”的算法，因为 vLLM 底层的块表只认从 0 开始的连续整数计数，在中间挖洞要么破坏位置编码，要么迫使 CPU 和 GPU 每步同步重排块表；
*   你也不能接管外层的解码循环去做投机解码（Speculative Decoding）的树分支回滚，或者从零预训练一个新模型架构——那些属于调度器外环与分布式训练框架的领地。

每当遇到这类越界组合，pLLM 的铁律是 **Fail-Closed（闭合失败）**：在触碰 GPU 之前直接报错并说明物理原因，不会一声不吭地关掉 CUDA Graph 退回慢路径（默认 `cuda_graphs="auto"` 下少数暂时进不了图的写法会以 eager 运行，但原因写在 `explain` 里；设 `cuda_graphs=True` 则直接报错），也绝不悄悄把塞不下的显存溢写到 CPU 内存里去制造隐蔽的线上事故。

1.  **[《行模型：在连续批处理里找回“每个请求”》](04-packed-rows.md)**
    面对拍扁的 `[num_tokens, hidden]` 张量，怎样在不改造引擎内部结构的前提下认出每一行是谁？讲讲当年我们在 vLLM C++ 注意力层外打断点追查 `attn_metadata` 的地下城探险，以及后来为何顿悟“入口处的三个整数就够推导一切”（文末附 vLLM 注意力元数据的实测解剖图鉴）。
2.  **[《Python 只在录制时活着：固定地址、一张表、零同步》](03-whole-algorithm-in-cuda-graphs.md)**
    当 Python hook 在图回放时人间蒸发，怎样把包含前向、反向传播和 `AdamW` 的整步在线训练完完整整录进 CUDA Graph？我们会从 1 个请求一路推演到可变请求数的哑槽（Sink）与二级指针解引用，并看看为什么给训练步套上 `torch.compile` 反而会变慢。
3.  **[《PTTS：给每个请求一块会“长版本”的显存》](01-ptts.md)**
    图地址固定、双流读写并发、半途导入新参数、抢占回滚——这四起看似无关的工程事故，为什么本质上都在呼唤同一个原语（带不可变版本号与写时复制的分页状态池）？
4.  **[《图内挂载点：在 CUDA graph 里改残差》](05-in-graph-attach-points.md)**
    Transformer 的残差加法被上游吞进了下一层的 `fused_add_rms_norm` 里，我们怎么在那里挂载代码？以及一场性能破案：当一行什么都不做的 `return x + y` 让吞吐掉到 65.8% 时，我们是怎么数出那多出来的 61,440 个 kernel，并用 `make_fx` 剪掉末尾加法追回 99.5% 的。
5.  **[《参数覆盖层：顺着 PyTorch 的抽象层往下走》](06-parameter-overlays.md)**
    论文里的 In-Place TTT 公式只有几行，却写死了 `batch_size == 1`。怎样把 `vmap`、`grad`、`compile`、`custom_op` 和 `make_fx` 像洋葱一样一层层叠起来，让它同时服务 128 个请求，并用“全局/分片双图同构”证明多卡 TP 下的更新完全不需要跨卡通信？
6.  **[《自定义层循环与状态传播》](10-custom-layer-loops.md)**
    当某个 token 在第 16 层决定提前早退，下一个 token 在第 17 层做注意力时一脚踩空怎么办？看看如何一行新 kernel 都不写、“借壳”原生注意力模块补齐 KV，以及为什么在 decode 阶段跳过 23% 的 token 一点也不会变快。
7.  **[《可编程注意力与 KV 布局》](08-programmable-attention-kv.md)**
    剖析 vLLM v1 记账的三条硬不变量：为什么“注意力少读一半”不等于“显存少占一半”？为什么 SnapKV 式的按分动态驱逐在不拆引擎的前提下无解？以及怎样把窗口、保留首段（R-SWA）和跨层共享伪装成上游认识的三种原语。
8.  **[《复用上游：kernel、管理器与原语》](09-reusing-upstream-kernels.md)**
    我们满怀善意地删掉手写 Triton kernel、改调上游标准的 FlashAttention-2 窗口接口，结果吞吐当场暴跌 21%，单次读取慢了 5 倍。这次翻车教会了我们扩展层的生存法则：复用的最小单位不是上游的某个函数，而是上游自己的执行路径。
9.  **[《采样尾声融合》](07-sampler-epilogue.md)**
    在 152,064 词的词表张量上每多扫一遍，都是在烧显存带宽。看我们如何立下“绝不新增任何一遍词表遍历”的铁律，用 `uint64` 的 IEEE 754 位翻转黑魔法和尾声融合（Epilogue Fusion），把采样引导塞进原本就有的三次扫描里。
10. **[《有界的零拷贝 gather 与预取》](12-bounded-zero-copy-gather.md)**
    几百兆的查找表放进主机内存，每步跨 PCIe 搬运要 1.6 ms。为什么一个发射 9,600 个线程块的朴素后台 gather kernel 会把前台的矩阵乘活活饿死，而把线程块砍到 SM 数的四分之一（32 个块）反而能同时打满 23.7 GB/s 总线并藏住九成以上的延迟？
11. **[《自动放置与重叠》](11-automatic-placement-overlap.md)**
    我们曾把连同依赖共 45 万行代码的 ISL 多面体库引进仓库，用来自动求解任务放置与跨步重叠；不到两个月后，我们又亲手提交了一个删掉四十多万行代码的 commit 把它彻底埋葬，换成了 40 行 Bellman-Ford 最长路。这是一个关于“一致依赖”、“GPU 重叠的零和真相”以及“主动约束系统复杂度”的故事。
12. **[《在 serving 引擎里信任一段用户程序》](02-trusting-user-programs.md)**
    回到 eBPF 的起点：当形式化证明在任意 PyTorch 代码面前失效时，怎样把“连续批处理的调度”本身变成可摆布的三元组数据，用一行加盐一百万（`salt = 1_000_000`）的差分测试，在装载前看住多租户隔离与抢占安全的底线？

纵观整个系统软件史，底层的执行引擎永远在追求**静态**——固定的地址、固定的形状、提前录好的图，因为只有静态才能把硬件压榨到极限；而上层的算法永远在追求**动态**——每个请求各异、每一步都在演化、随时根据上下文调整结构。

这个系列里的每一项技术，说到底都是在静态的岩石与动态的流水之间，凿出一条精密的接缝：**让会变的一切变成表里的数据，让不变的机器全速运转。**
