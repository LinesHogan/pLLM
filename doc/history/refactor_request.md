# 附加计算负载自动调度系统架构报告

## 1. 引言：问题定义与系统目标

### 1.1 是什么

本系统旨在解决**主计算负载与附加计算负载的联合调度问题**。具体而言，存在一个高性能的主计算引擎（如大规模语言模型推理系统），在其执行过程中，用户希望注入额外的计算任务（如数据压缩、特征提取、日志编码、辅助推理等）。这些附加负载具有如下特征：

- **计算逻辑由用户定义**：用户清楚描述其输入输出语义；
- **执行时机可弹性调整**：附加负载对延迟的敏感度通常低于主计算，可以在主计算时间轴上的一定窗口内浮动执行；
- **存在并行优化空间**：通过将附加负载拆分为子任务，并将其重新安排（reschedule）到主计算的不同时期，可以实现计算与计算、计算与数据搬运之间的重叠（overlap），从而提升整体吞吐量或降低端到端延迟。

系统的核心目标是：**在用户仅提供附加负载的计算描述的前提下，自动将其拆分、调度并优化执行顺序，使其与主计算负载高效协同，同时保证语义正确性和资源约束的可满足性。**

### 1.2 动机

现代深度学习推理系统（尤其是大模型推理）已经将 GPU 算力和内存带宽压榨到接近物理极限。主计算负载本身经过高度优化（如算子融合、CUDA Graph、连续批处理等），其执行时间轴上的空隙极小。在这种背景下，任何额外的计算任务如果采用简单的"顺序追加"方式执行，都会直接增加端到端延迟，甚至导致内存溢出。

然而，附加负载往往具有**可分解性**和**可延迟性**。例如，一个对中间激活值进行压缩的附加任务，可以被拆分为多个子任务，分别在不同的层之间执行；某些子任务甚至可以与主计算的内存密集型操作重叠。这种优化机会无法通过手工编排实现，因为：

- 主计算负载的图结构复杂且频繁变化（不同模型、不同框架版本）；
- 数据依赖关系跨越多层，人工分析容易出错；
- 硬件执行细节（如 CUDA Stream 同步、内存池状态）难以手动建模。

因此，需要一个**自动化的调度系统**，在编译时或运行时分析主/附负载的联合数据流，自动推导最优执行计划。

## 2. 系统定位：编译器中端（Middle-End）的调度综合层

### 2.1 是什么

本系统在整体编译/执行栈中的定位是**调度综合层（Schedule Synthesis Layer）**，位于编译器中端（Middle-End）。它既不属于传统意义上的前端（负责图捕获和语法分析），也不属于后端（负责寄存器分配和指令生成），而是介于两者之间的一个专门层：

```
┌─────────────────────────────────────┐
│  前端：图捕获与表示（FX Graph/AST）  │
├─────────────────────────────────────┤
│  ★ 中端：调度综合层（本系统）         │
│    - 联合依赖分析                    │
│    - 子任务拆分与拓扑排序             │
│    - 多面体调度优化                   │
│    - 内存规划与约束满足               │
├─────────────────────────────────────┤
│  中端-后端边界：Lowering              │
├─────────────────────────────────────┤
│  后端：代码生成与硬件执行             │
└─────────────────────────────────────┘
```

### 2.2 为什么是这个位置

调度综合层必须满足两个前提：

1. **必须看到完整的图结构**：只有在图捕获完成后，系统才能分析主计算与附加负载之间的数据依赖关系，找到可以插入子任务的合法时间窗口（slack）。在前端阶段，图结构尚未实例化，无法进行全局分析。

2. **必须在代码生成之前**：调度决策改变的是"哪些计算在什么时间、以什么粒度、在什么并行度下执行"，而不是"如何用机器指令表达某个算子"。如果在 lowering 之后介入，循环结构已经固化，重排空间将极其有限。

对于采用**分块编译（piecewise compilation）**的系统（如将模型按层或按模块切分为多个子图分别编译），系统需要具备**双层介入能力**：

- **层内（Intra-piece）**：在每个独立的编译单元内部，通过自定义编译流程中的变换阶段，对附加负载子图进行节点移动、融合和重排；
- **层间（Inter-piece）**：在图切分之前，对完整的全局图进行跨模块的 reschedule 决策，确保被切分到不同编译单元的子任务之间保持正确的执行顺序和数据传递。

这种双层定位确保系统既能利用现有编译基础设施的优化能力，又能在必要时突破单编译单元的边界。

### 2.3 怎么样

系统的介入遵循**"只决策、不生成"**的原则：

- **输入**：主计算负载的图表示（包含算子节点、张量边、控制流信息）+ 附加负载的计算描述；
- **处理**：Rust Core 作为调度决策引擎，输出一个**结构化调度决策**（包含子任务列表、插入锚点、并行策略、内存分配方案）；
- **输出**：调度决策交由现有编译基础设施执行具体的图变换和代码生成。

系统不直接生成 Triton、CUDA C++ 或 LLVM IR，而是将调度决策表达为对现有 IR 的变换指令，由框架原生的 lower 和 codegen 完成最终代码生成。

## 3. 技术选型

### 3.1 Rust Core：调度决策引擎

系统的核心算法承载于 Rust 实现。选型理由：

- **性能**：多面体调度涉及大量整数集运算和线性规划求解，Rust 的零成本抽象和无 GC 特性确保算法层不会有不可预测的停顿；
- **类型安全**：调度图、依赖关系、内存规划等数据结构具有复杂的内部一致性约束，Rust 的类型系统和所有权模型可以在编译期消除大量运行时错误；
- **FFI 友好**：Rust 与 C 库（如 isl）的互操作成本极低，且不需要像 Python 那样在运行时做大量的类型判断和对象装箱。

Rust Core 的职责被严格限定为**调度决策**：它接收一个抽象的调度图（Schedule Graph），输出调度决策（Schedule Decision）。它不关心 FX Graph 的具体节点类型，也不直接操作 Python 对象。

### 3.2 多面体引擎：Tadashi / isl

系统复用现有的多面体编译技术，而非自研调度算法。具体而言，采用基于 **isl（Integer Set Library）** 的调度引擎（如 Tadashi），其内置 **Pluto 算法**。

选型理由：

- **自动 Wavefront 提取**：Pluto 算法通过整数线性规划自动寻找最优仿射调度，能够自动发现 loop skewing（倾斜）机会，将串行依赖转换为对角线并行（wavefront），无需人工推导变换矩阵；
- **合法性保证**：多面体引擎自动验证任何变换（tiling、interchange、skewing、fusion）不会破坏数据依赖，避免人工实现依赖分析的错误；
- **丰富的变换原语**：内置 tiling、loop interchange、full/partial shift（skewing）、parallelization、fusion 等原语，覆盖绝大多数优化场景；
- **成熟的 C 库 + Python/Rust 绑定**：isl 是工业级多面体库，被 PPCG、Polly、Pluto 等生产编译器采用，稳定性经过验证。

系统的 Rust Core 通过 FFI 调用 isl 的依赖分析和调度功能，将多面体优化作为黑盒引擎嵌入，自身只负责**桥接层的图转换**和**跨负载的拓扑编排**。

### 3.3 复用而非重复

系统明确不重复造轮子的部分：

| 功能 | 复用来源 | 本系统不实现 |
|------|---------|------------|
| 图捕获 | 框架原生 Dynamo/Tracer | 图捕获逻辑 |
| 自动微分 | 框架原生 AOT Autograd | 反向图生成 |
| 算子分解 | PrimTorch / ATen | 算子 lowering |
| 依赖分析（多面体） | isl / Tadashi | 整数线性规划求解器 |
| 代码生成 | Inductor / Triton / LLVM | 指令选择和寄存器分配 |
| 编译缓存 | 框架原生 FX Graph Cache | 缓存键值管理 |

本系统唯一需要自研的部分是：
1. **IR Bridge**：将框架的图表示转换为调度引擎可理解的抽象调度图；
2. **跨负载拓扑编排**：决定附加负载的哪些子任务插入到主计算的哪个锚点；
3. **Memory Planner**：在调度约束下规划缓冲区生命周期。

## 4. 软件架构

系统采用分层架构，各层职责如下：

### 4.1 IR Bridge（Lowering 桥接）

IR Bridge 是框架图表示与 Rust Core 之间的翻译层。它的职责是：

- **序列化**：将主计算图和附加负载子图提取为一个与框架无关的**调度图（Schedule Graph）**。调度图的节点表示计算子任务，边表示数据依赖和执行顺序约束；
- **元数据提取**：标注每个节点的读写张量信息（形状、数据类型、内存布局）、计算复杂度估计；
- **纯函数性验证**：检查附加负载是否满足无副作用、无 I/O、无动态控制流的约束，若不满足则在编译时报错而非静默失败。

IR Bridge 是系统与具体框架（PyTorch、TVM、JAX）的唯一耦合点。当框架版本升级或更换框架时，只需要修改 Bridge 的实现，Rust Core 完全不受影响。

### 4.2 Rust Core：Schedule Decision Engine

Rust Core 是系统的"大脑"，包含以下子模块：

- **Dependency Analyzer**：调用 isl 计算主计算与附加负载之间的 flow/may/must 依赖关系；
- **Polyhedral Scheduler**：调用 Tadashi/isl 对附加负载子图进行多面体变换（tiling、skewing、parallelization）；
- **Wavefront Extractor**：在合法变换空间中识别可并行的 wavefront 结构；
- **Topology Sorter**：对跨主/附的混合任务图进行拓扑排序，确定子任务的执行顺序；
- **Cost Model**：评估每种调度方案的预期代价。Cost Model 将**数据搬运成本**作为一等公民，其权重远高于纯计算成本。公式形式化为：
  
  ```
  total_cost = α × compute_cost + β × memory_cost + γ × transfer_cost
  ```
  
  其中 `γ >> α`，以反映现代 GPU 架构中数据搬运是瓶颈的物理现实；
- **Memory Planner**：在调度搜索过程中维护峰值内存估计，将用户提供的内存预算作为**硬约束**。任何导致峰值内存超支的调度方案都会被剪枝（prune）。

### 4.3 Validation Layer

Rust Core 输出调度决策后，Validation Layer 负责在应用前进行静态验证：

- **依赖正确性**：使用 isl 重新计算 reschedule 后的依赖图，确认无循环依赖、无丢失写操作；
- **内存生命周期**：验证每个缓冲区的分配点覆盖所有读写访问，释放点在所有使用完成之后；
- **数值等价性（可选）**：通过随机测试验证 reschedule 前后的数值结果在允许误差范围内一致。

Validation Layer 是系统的"安全网"。即使调度算法存在 bug，Validation Layer 也能在代码生成前拦截错误。

### 4.4 Backend Abstraction

Backend 是系统向下对接主计算负载执行框架的抽象接口。它定义了框架必须提供的能力：

- **图遍历**：按拓扑序遍历计算节点；
- **节点操作**：在指定锚点后插入新节点、删除旧节点；
- **张量查询**：查询某节点的输入输出张量元数据；
- **内存接口**：申请和释放缓冲区，支持 inplace 复用。

系统通过 Backend trait（或接口）支持多种框架。当前聚焦某一框架时，实现对应的 Backend 即可；未来扩展时，Rust Core 无需修改。

### 4.5 Runtime Orchestration

Runtime 负责将 Rust Core 的调度决策转化为实际的执行时序。在推理引擎场景下，这通常涉及：

- **执行流管理**：决定附加负载子任务在主计算的哪个执行流（如 CUDA Stream）上运行；
- **同步策略**：决定子任务与主计算之间是否需要显式同步（如 Event/Barrier），以及同步点的位置；
- **异步 Overlap**：在不需要数据依赖等待的情况下，允许附加负载与主计算并行执行。

Runtime 是调度决策的"执行器"，它本身不做调度决策，只负责忠实地执行 Rust Core 输出的计划。

### 4.6 Cache / Persistence

调度决策可以被缓存以避免重复编译。缓存的键应包含：

- 主计算图的签名（结构哈希）；
- 附加负载的计算描述签名；
- 调度策略配置；
- 内存预算约束。

当任何一项发生变化时，缓存自动失效，重新触发调度。

## 5. 核心设计原则

### 5.1 数据搬运为一等公民

现代 GPU 的算力远超内存带宽，计算本身往往是"免费的"，数据搬运才是瓶颈。因此：

- Cost Model 中 `transfer_cost` 的权重最高；
- 调度搜索优先选择**零额外搬运**的方案（如 inplace 复用主计算的废弃激活值）；
- 跨设备（CPU-GPU、GPU-GPU）的搬运只有在计算收益显著高于搬运成本时才被允许。

### 5.2 内存预算是硬约束

在大模型推理场景中，GPU 内存通常已被主计算负载（KV Cache、模型权重、激活值）占满。系统必须将用户或环境提供的内存预算作为**不可逾越的边界**：

- 默认调度策略为**顺序重叠（in-order interleaving）**：在主计算的两个算子之间的天然间隙执行附加负载子任务，不增加并行 buffer；
- Wavefront 并行（需要为每个并行波次分配临时 buffer）仅在内存预算明确允许时才启用；
- Memory Planner 在调度搜索的每一步都进行峰值内存估算，超支即剪枝。

### 5.3 算法与调度分离

用户只描述**计算逻辑**（what），系统全权决定**调度策略**（how）。这种分离确保：

- 用户无需理解 wavefront、tiling、loop skewing 等概念；
- 调度策略可以随硬件和框架版本升级而自动改进，用户代码无需修改；
- 系统支持渐进式控制：用户可以通过策略约束（如"禁用 wavefront"）限制搜索空间，但不暴露底层变换参数。

### 5.4 纯函数性假设

附加负载必须满足纯函数约束：无副作用、无 I/O、无外部状态、无数据依赖的动态控制流。这是系统能够安全 reschedule 的前提。系统在编译时通过静态分析验证此假设，若不满足则拒绝调度并给出明确错误。

### 5.5 可信赖性优先于可视化

系统的首要目标是成为**可信赖的基础设施**，用户默认信任其输出。因此：

- 提供可验证的执行摘要（如"附加负载被拆分为 N 个子任务，预期延迟降低 X%，峰值内存增加 Y%"）；
- 可视化（如时序图、交互式编辑器）是辅助工具，不是核心功能；
- 所有调度决策均可追溯：系统记录每个决策的代价模型估计和实际运行反馈。

## 6. 调度策略与默认行为

### 6.1 默认策略：顺序重叠

在内存预算未明确放宽的情况下，系统默认采用**顺序重叠**策略：

- 将附加负载拆分为尽可能小的子任务；
- 每个子任务被插入到主计算时间轴上**数据依赖允许的最晚位置**；
- 子任务与主计算之间不引入额外的并行 buffer，仅利用主计算的自然间隙。

这种策略的内存开销最小，且在任何内存压力下都安全。

### 6.2 内存复用策略

当主计算的某些中间激活值在后续步骤中不再被使用时，Memory Planner 会将其缓冲区标记为可回收。附加负载的子任务可以**复用这些缓冲区**作为输入或输出，避免额外的内存分配。

### 6.3 跨子图/跨模块约束

如果附加负载的子任务需要分布在主计算的多个模块（或编译单元）之间执行，系统要求：

- 子任务之间**不共享隐式状态**（如全局变量、静态缓冲区）；
- 子任务之间的数据传递必须通过**显式张量**进行；
- 每个子任务在其插入点的局部上下文中是独立的。

## 7. 正确性与安全

### 7.1 数值等价性

系统接受**近似数值等价**而非 bit-wise 相等。Reschedule 可能改变浮点运算的顺序（如 reduction 的累加顺序），导致微小数值差异。这在深度学习推理中通常是可接受的。

系统不保证 bit-wise 相等，但保证：
- 对于确定性计算，reschedule 不改变输出分布的统计特性；
- 对于需要梯度的情况（附加负载本身需要反向传播），只要其内部计算拓扑不变，反向传播的正确性不受影响。

### 7.2 合法性保证

所有多面体变换（tiling、skewing、interchange 等）的合法性由 isl 自动验证。系统不会应用任何被验证为非法的变换。跨主/附的拓扑重排由 Rust Core 的 Topology Sorter 基于显式数据依赖边进行，确保无循环依赖。

### 7.3 失败策略

当调度算法无法找到满足所有约束（内存预算、数据依赖、设备能力）的方案时，系统应：

- **优雅降级**：回退到最简单的顺序执行模式（附加负载在主计算完成后统一执行）；
- **明确报错**：如果回退也无法满足约束（如附加负载的输入在主计算结束后已被释放），在编译时给出清晰的错误信息，说明冲突的依赖关系。

## 8. 产品形态哲学

### 8.1 声明式接口

用户通过声明式方式描述附加负载：提供计算函数、指定其输入来源（主计算的哪个中间结果）、以及高层策略偏好（如"自动"、"优先重叠"、"保守内存"）。系统负责将声明转化为具体调度。

### 8.2 透明优化

系统对用户是**透明**的：用户不需要理解调度细节，只需要感知性能提升。系统提供足够的信息让用户验证优化确实发生，但不强制用户参与决策。

### 8.3 渐进式控制

系统支持**策略约束**：用户可以在不暴露底层变换参数的前提下，启用或禁用特定类别的优化（如"允许 tiling，但禁用 wavefront"、"限制最大 tile size"）。这些约束被输入到 Rust Core 的调度搜索空间中，作为剪枝条件。

## 9. 风险、边界与演进

### 9.1 动态形状

当前系统限定为**静态形状**假设。调度决策在编译时基于已知的张量形状做出，缓存键也包含形状信息。对于动态形状场景（如变长序列、变 batch size），每次形状变化都会触发重新调度。在推理引擎中，这通常与引擎自身的调度粒度（如每次 forward 前的 batch 组装阶段）对齐，因此不构成致命障碍。

### 9.2 框架版本隔离

系统通过 Backend Abstraction 隔离与具体框架版本的耦合。当底层框架（如 PyTorch）升级导致图表示或编译接口变化时，只需要更新 Backend 实现，Rust Core 和调度算法完全不受影响。

### 9.3 性能回退与反馈

系统内置 Cost Model 进行调度前预估，但预估可能与实际硬件行为存在偏差。因此系统需要：

- **运行时 Profiling**：收集每个子任务的实际执行时间和内存带宽占用；
- **反馈闭环**：将实际数据反馈给 Cost Model，用于改进后续调度的预估精度；
- **诊断接口**：在性能未达预期时，提供决策追溯（某子任务为何被安排在此处，预期收益是多少）。

## 10. 总结

本系统是一个位于编译器中端的**调度综合层**，核心使命是在不修改主计算负载的前提下，自动将用户定义的附加计算负载拆分、优化并重新安排到主计算时间轴上，以实现计算重叠和延迟隐藏。

系统的核心设计哲学是**"复用成熟算法，专注独特价值"**：多面体调度（wavefront、tiling、合法性验证）复用 isl/Tadashi 等工业级库；本系统自研的部分聚焦于**跨负载的拓扑编排**、**内存感知调度**和**与深度学习框架的桥接**。

系统采用 Rust 承载核心调度算法以保证性能和类型安全，通过抽象 Backend 接口与具体框架解耦，并以内存预算作为硬约束确保在大模型推理场景下的安全性。默认策略优先选择内存开销最小的顺序重叠，仅在资源允许时启用更激进的并行策略。

最终，系统对用户呈现为**透明、可信赖的基础设施**：用户描述计算，系统自动优化，所有复杂性被封装在内部。
