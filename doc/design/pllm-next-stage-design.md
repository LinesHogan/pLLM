## 1. 定位与名称

建议把项目名称从 tLLM 调整为 **PLLM，Programmable LLM**。框架的核心不只是
test-time training，而是让用户显式编写对推理计算、状态、梯度和控制流的修改，
由系统在保持算法语义的前提下执行和优化。

品牌名、发行包名、import 路径可以分别决定。若决定迁移，先列出源码、打包、CLI、
文档、示例和 wire/schema 中的实际引用，再确定一次性切换及必要的迁移说明。
不要为更名建立长期双 runtime 或复制两套公共实现，也不要机械替换持久化身份而破坏重建。

## 2. 收缩自动适配承诺

目标不是把任意 Python/PyTorch 程序自动转换成高性能分页实现，而是提供一套人和
coding agent 都能正确使用的、显式且可验证的高性能编程契约。

用户可以先描述算法或给出朴素 reference，再让自己的 coding agent 按契约重写 workload。
适配主要发生在开发期，结果是正常维护的源码，不是每次运行时的临场代码生成。
人工开发遵循同一契约，不要求使用特定厂商、模型或在线服务。

框架承诺：

- 符合契约的数学、状态和 effect 能进入同一编译与执行路径。
- 已支持的计算模式可以显式绑定共享高性能原语，不要求透明识别所有用户写法。
- 不支持的语义在边界明确拒绝；实现覆盖范围和执行成本可检查。
- 正确性由类型、编译校验、资源 owner 和独立行为证据共同约束，不由 agent 的解释担保。

框架不承诺任意 Python 控制流、隐藏原地修改、动态模块结构或任意 autograd 程序都能
自动合批和融合。模板特化可以服务 kernel 的 shape/dtype，但不是 workload 的编写方式。
不为避免要求用户配合，而建设巨大的反射、兼容或自动重写框架。

## 3. 推荐开发流程

```text
算法描述与朴素 reference
    -> 用户确认数学、状态、梯度和时序语义
    -> coding agent 按框架契约适配
    -> typed 声明 + 数学实现 + 已有原语绑定
    -> 独立数值、生命周期和性能检查
    -> 审查源码
    -> 正常编译、签名、执行
```

Agent 可以修改 workload 的声明、数学和对应证据，但不得自行改变算法来满足性能目标。
输入事实不完整时，应指出缺少的选择，例如 global 梯度是聚合更新还是逐请求更新，
而不是凭经验选一个并称作等价迁移。

Reference 的语义和版本先固定。不能让 agent 同时改 reference 和优化实现，再以两者
一致证明正确；必要的语义修订必须单独审查。测试只能提供其覆盖范围内的证据，不能
把少数样例通过当作任意输入上的等价证明。

Agent 交付物应紧凑：源码差分、所依据的 reference、验证结果、支持边界和性能代价。
不要求为每个 workload 再生成一套设计文档、服务层和调度器。
运行时不调用 agent、不下载其生成代码、不依赖提示词或模型版本才能重现行为。

## 4. 给 Agent 的契约材料

使用入口现为[让你的 Agent 编写 Workload](guides/agent-workloads.md)：包含用户必要信息、
可复制委托模板、按算法选择的真实范例和 agent 交付约定；API 仍以编写契约为准。

第一版只需一个短入口，链接权威 API、维护中的真实范例和可执行检查；暂不建设 agent
平台、对话编排服务或提示词框架。以后可封装成 skill，但 skill 不成为另一份规范。

| 材料 | 必须回答的问题 |
| --- | --- |
| 数学编写约定 | 输入输出如何声明，哪些操作受支持，何处允许自定义计算 |
| 状态/effect 约定 | request/global、读版本、私有写入、发布点、KV/RNG/host 外部动作 |
| 梯度约定 | 输入梯度、参数梯度、截断、loss 归约和 optimizer 更新资格如何区分 |
| 原语目录 | 操作、shape/dtype、布局、反向支持、设备、capture 条件及临时容量 |
| 真实范例 | 同一 vLLM batch 内的独立参数、共享参数、选择性训练如何表达 |
| 验证入口 | 数值、版本隔离、取消、结算和性能证据如何运行与解释 |

材料随 API 同批更新，范例直接复用维护中的 workload 和测试，避免文档自带一套过时实现。
检查器报告具体 operation/state 和违反的约束，并给出契约定位。

可检查的规则尽量自动检查，例如不允许 workload 持有版本库或选择物理页。静态检查不能
证明的任意 tensor 别名、外部副作用或数值等价问题，要明确保留运行验证和人工审查。
不能用“agent 应该懂”替代一个清楚的接口，也不能堆叠启发式检查假装已证明安全。

## 5. 共享边界与页表感知计算

执行、AER、PTTS、replay、MP 和 trace 仍共享原始 SemanticGraph、计划、状态身份和
issued receipt。概念上有不同职责，不意味着各维护一套可修改的数据结构。

用户数学使用逻辑参数和输入 tensor。物理实现根据已授权的状态选择访问页池：

```text
数学操作与逻辑状态输入
    -> 已签定的实现与 exact version 选择
    -> arena 所拥有映射的设备端表示
    -> 页池上的 batched/grouped kernel
```

GPU 页表或 row-to-state 索引是原始边界的派生执行表示，不是第二版本库。其生成、更新、
失效和完成顺序必须由同一 owner 管理；在途 kernel 使用的表项不能被下一批覆盖。
kernel 不猜 latest、不签发逻辑版本、不绕过发布或回收。

必须区分三种支持等级：

1. **语义可执行**：借用 tensor 视图或明确打包后调用普通实现。
2. **原生分页执行**：计算 kernel 直接按状态映射读取页池，避免展开整份参数。
3. **融合与 capture**：满足声明的布局、地址及动态控制条件后，再合并操作或复用图。

普通 tensor 路径可以是规划器事先选择的合法实现，其临时空间和搬运成本必须计入计划；
禁止失败后偷偷 fallback。必要的数据打包并不等于复制语义 authority，但也不能隐藏成本。
池地址稳定不等于跨版本 CUDA Graph 可用。实现前需重新核实当前能力，不沿用旧状态报告。

## 6. 混合请求与选择性反传

vLLM 的一个 batch 可以包含需要不同 workload 行为的请求，不应由 Python 逐请求启动
完整 forward/backward/optimizer 流程，也不必把所有请求强制放入同一种执行模式。

分组依据是操作、布局、dtype、梯度需求以及依赖/effect 约束，不是 workload 名称。
不同版本可同批计算，但每行仍读其 exact pin 对应的参数。

- forward 行集、参数梯度行集、输入梯度行集和允许更新的状态集分别表达。
- 不训练的行可以参与 forward，但无需保存不需要的反向中间值。
- 冻结参数不一定能省略 backward：前序可训练操作可能仍需要输入梯度。
- 零梯度不等于跳过 AdamW；step、momentum 和 weight decay 也必须遵守更新资格。
- 多行共用状态时，明确 loss 的归约范围、归一化方式和梯度归属。
- global 一次聚合更新与多个顺序更新通常不等价；合批不得擅自替换。
- request 内存在逐 token 更新依赖时，不能为方便 GEMM 而跨越可见性边界。

固定容量加 mask、按活跃行压紧、按形状分桶各有代价：padding 浪费计算，压紧需要
选择/扫描，分桶可能增加 launch。选择应来自真实负载和成本事实，而非写死一种最佳策略。
数据依赖的训练条件还需声明 predicate 的可用时间，不得把未完成的 GPU 条件交给 host 猜测。

## 7. 优先建设的高性能原语

先测量，再选择跨至少两个实际场景复用的部分。不建立万能神经网络 kernel，也不要求
每个 workload 自带 CUDA/Triton 实现。

| 优先候选 | 主要消除的开销 | 关键约束 |
| --- | --- | --- |
| 页表感知 batched/grouped linear 及反向 | 逐请求 GEMM launch、按 token 展开的重复参数 | exact pin、异形分组、参数与输入梯度 |
| 按状态分段的梯度/loss 归约 | 独立小归约、共享状态重复计算 | 归约语义、累加精度、确定性要求 |
| 多字段 fused optimizer | 每个 root 多次逐元素 launch | 私有页、更新 mask、step 与 moments 一致 |
| 稳定 row/state 索引及选择操作 | 每步小分配、host 到 device 搬运和同步 | 固定容量、表项生命周期、捕获资格 |

页表解引用优先融入消费它的计算；单独 gather 后仍大规模复制参数，不应被称作最终优化。
显式原语绑定是首选，常见计算图模式识别可后加，不以全自动 lowering 为首轮前提。

优先复用成熟 GEMM 库。Triton 可用于索引、mask、归约和优化器融合；CUDA/CUTLASS 用于
确有收益的复杂矩阵或运行时集成。设备语言选择不是验收目标，不因某种实现“原生”就认定更快。
特化数量与编译缓存应有边界，避免动态 request/版本身份导致无限重新编译。

其余需测量的瓶颈包括：host 行映射与调度、`.item()` 引起的同步、逐字段 COW/copy、
激活捕获与保存、临时分配、内存带宽、梯度累加冲突和过度 stream/event 管理。
并行不能突破有因果依赖的更新顺序；减少 launch 也不能以显存失控或增加大量无效计算换取。

## 8. 验收与实施顺序

本阶段开始前先确认当前完整计划已验收，再重新 profile，不能把中间实现的瓶颈当成
终态事实。继续使用现有证据清单和计数规则，不平行建立另一套测试体系。

1. **确定契约和名称。** 审查命名可用性；从两个真实场景提取最小编写契约和原语边界。
   退出条件：用户与 agent 能明确知道支持什么、不能做什么，不需要猜测内部约定。
2. **完成共享高性能替换。** 先保留独立数学 reference，按测量选择一组原语，原子替换
   逐请求执行或参数展开路径。退出条件：原始版本/receipt 边界不变，重复实现被删除。
3. **验证 agent 适配流程。** 用未参与接口设计的算法变体，仅给 agent 契约、范例和 reference。
   记录需要的人类澄清、重写次数、核心修改范围及失败原因；失败不能靠恢复专属 runtime 解决。
4. **完成研究与发布评估。** 对比普通合法实现、认真优化的专用实现和共享优化实现；验证源码、
   kernel 特化、环境和计划可重现。名称迁移若获确认，在此独立执行并检查打包/import/文档。

正确性必须覆盖输出、梯度、optimizer 状态、无更新分支、跨请求隔离、版本 pin、COW、
取消和完成前禁止回收。参考计算不调用被测实现的同一数学 helper。
数值容差、归约顺序变化和确定性要求事先约定，不能为通过测试事后放宽。

性能变化覆盖请求数、每请求行数、训练比例、共享状态比例、rank/shape 和内存压力。
报告端到端延迟/吞吐、CPU 提交时间、GPU 时间、launch 数、搬运字节、临时峰值与实际更新量。
将冷编译、预热和稳态分开；相同算法与有效工作量才能比较，不能用少训练或零更新制造收益。
分析显示 launch 或复制主导时，原语应减少对应成本；实际不受这些成本限制的场景不承诺加速。

最终成功不是“agent 写出了能运行的代码”，而是：新 workload 可以通过局部、可审查的修改
表达算法，复用共享高性能机制，证明语义保持，并且核心没有增加镜像状态、兼容层或专属编排。
